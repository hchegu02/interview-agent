# 亮点 4：显式降级与集中可观测性（DegradedReasons 强类型表）

> 代码位置：`internal/domain/agent.go`（WorkingMemory）、各 `internal/nodes/*.go` 的降级路径、`internal/nodes/report.go`、`internal/observability/`
> 核心思想：**不静默吞错**——所有降级路径必须显式记录，统一汇总到报告
> 面试官追问命中率：★★★★（工程纪律的硬证据）

---

## TL;DR（30 秒讲清楚版）

> 这个项目有一条铁律：**不静默吞掉任何外部依赖失败**。所有 LLM 调用 / RAG 检索 / Redis 操作失败时，节点必须做两件事：
>
> 1. **走规则 fallback 路径**继续推进（不阻断主流程）
> 2. **显式写入** `WorkingMemory.DegradedReasons[component] = reason`（强类型 map，component 用稳定名）
>
> 最终 `Report.NextSteps` 自动汇总所有降级组件，提示用户"评估时 X 环节降级了，建议重测以提高可信度"。
>
> 关键判断：**"降级"和"阻断"的边界**——质量下降可降级（评估、检索），所有权破坏必阻断（Lease）。

## 一、为什么需要"显式降级"

### 1.1 反面教材

大量项目里这种代码到处都是：

```go
// ❌ 静默吞错的反面教材
func evaluate(ctx context.Context, sess *Session) error {
    score, err := llm.Score(ctx, answer)
    if err != nil {
        log.Println("score failed:", err)  // 打 log 就完了
        score = 50                          // 默认给个分
    }
    sess.WorkingMemory.LastScore = score
    return nil
}
```

**问题**：
- 用户拿到分数，**不知道这是 LLM 评估还是默认值**
- log 在生产环境很难追踪到具体哪个用户哪个 session
- 出 bug 找不到原因（"为什么这个用户的分一直是 50？"）
- 监控告警写不出来（log 里"score failed"被淹没在十万条日志里）

### 1.2 显式降级的设计

```go
// ✅ 显式降级
func evaluate(ctx context.Context, sess *Session) error {
    score, err := llm.Score(ctx, answer)
    if err != nil {
        // 1. 显式标记降级
        markDegraded(sess, "eval", err.Error())

        // 2. 走规则 fallback（不静默用默认值）
        score = ruleBasedScore(sess, answer)
    }
    sess.WorkingMemory.LastScore = score
    return nil
}
```

**好处**：
- 用户报告里能看到"评估环节降级了"
- 监控可以告警"近 5 分钟 `DegradedReasons['eval']` 出现频率上升"
- 测试可以验证"LLM 失败时是否正确走 fallback 路径"
- **Bug 永远可追溯**

## 二、DegradedReasons 数据模型

### 2.1 数据结构

```go
type WorkingMemory struct {
    // ... 其他字段 ...

    // DegradedReasons 是降级原因的集中记录
    // key：稳定的 component 名（不要随便改）
    // value：人读的降级原因（错误信息或降级类型）
    DegradedReasons map[string]string
}
```

### 2.2 稳定的 component 命名规范

| component | 出现位置 | 典型 reason |
|---|---|---|
| `pick` | pick_next 节点 LLM 选题失败 | `llm_call_failed: timeout` |
| `eval` | evaluate 节点 LLM 评分失败 | `llm_breaker_open` |
| `critic` | critic 节点 LLM 判信号失败 | `schema_invalid` |
| `refine` | refine 节点二次评估失败 | `llm_call_failed` |
| `probe` | probe_ask/eval 追问失败 | `budget_exceeded` |
| `rag` | retrieve_rag 检索失败 | `pg_connection_failed` |
| `redis_snapshot` | Redis snapshot 写失败 | `network_timeout` |
| `event_publish` | SSE event 发布失败 | `redis_stream_busy` |
| `breaker_open` | 熔断器拦截 | `(自动添加)` |

**为什么 component 名要稳定**：
- 监控告警规则按 component 名写（改名会让告警失效）
- 报告模板按 component 名映射成人读文案

### 2.3 辅助函数（集中入口）

```go
// markSessionDegraded 是降级记录的唯一入口
// 防止散落各处的 sess.WorkingMemory.DegradedReasons[xxx] = yyy
func markSessionDegraded(sess *domain.Session, component, reason string) {
    if sess == nil {
        return
    }
    if sess.WorkingMemory == nil {
        sess.WorkingMemory = domain.NewWorkingMemory()
    }
    if sess.WorkingMemory.DegradedReasons == nil {
        sess.WorkingMemory.DegradedReasons = map[string]string{}
    }
    sess.WorkingMemory.DegradedReasons[component] = reason
}
```

**好处**：
- 所有降级都走同一个入口，**容易加 hook**（比如未来要打 metric / trace 直接在这里加）
- 防御性编程（sess/WorkingMemory/Map nil 检查全在一处）

## 三、节点降级模式（必须遵守的范式）

### 3.1 标准范式

每个节点内部分层：

```
run()                  顶层入口
  ↓
runByLLM()             调 LLM 的实现
  ↓ (失败时)
markDegraded() + ruleBased()   显式降级 + 规则 fallback
```

### 3.2 完整示例：evaluate 节点

```go
func Evaluate(ctx context.Context, sess *domain.Session) error {
    round := sess.CurrentRound()
    if round == nil {
        return fmt.Errorf("no current round: %w", graph.ErrPermanent)
    }

    // 优先走 LLM 评估
    eval, err := evaluateByLLM(ctx, sess, round)
    if err != nil {
        // 1. 分类错误，决定是降级还是冒泡
        if errors.Is(err, graph.ErrPermanent) {
            return err   // 永久错冒泡，不能降级
        }

        // 2. 显式记录降级原因
        markDegraded(sess, "eval", classifyEvalErr(err))

        // 3. 走规则 fallback
        eval = ruleBasedEvaluation(sess, round)

        // 4. 标记本轮为降级轮次（独立计数器）
        sess.WorkingMemory.DegradedRounds++
    }

    round.Evaluation = eval
    sess.WorkingMemory.ScoredRounds++
    return nil
}

// 规则 fallback：基于关键词匹配 + 长度的简单评分
func ruleBasedEvaluation(sess *domain.Session, round *domain.AnswerRound) *domain.Evaluation {
    // ... 简单规则评分 ...
    return &domain.Evaluation{
        Score:      ruleScore,
        Suggestion: "规则降级评分，建议复测",
    }
}

// classifyEvalErr 把各种 LLM 错映射成稳定的 reason 字符串
func classifyEvalErr(err error) string {
    if errors.Is(err, llm.ErrBreakerOpen)        { return "breaker_open" }
    if errors.Is(err, llm.ErrSchemaInvalid)      { return "schema_invalid" }
    if errors.Is(err, context.DeadlineExceeded)  { return "timeout" }
    if errors.Is(err, llm.ErrTransient)          { return "transient" }
    return "unknown"
}
```

### 3.3 为什么用 `classifyXxxErr` 而不是直接 `err.Error()`

```go
// ❌ 反面：reason 是 raw error message
markDegraded(sess, "eval", err.Error())
// reason = "Post https://api.qwen.com/v1/chat: dial tcp 1.2.3.4:443: i/o timeout"
// 问题：里面有 IP、URL、动态信息，难以聚合告警

// ✅ 正面：reason 是稳定的分类字符串
markDegraded(sess, "eval", classifyEvalErr(err))
// reason = "timeout"
// 监控规则可以写：rate(degraded_reasons{component="eval", reason="timeout"}[5m]) > 0.1
```

**这是 SRE 的标准实践**：**指标维度必须有限可枚举，不能放高基数字段**（IP、URL、用户 ID）。

## 四、降级 vs 阻断的判断公式

这是分布式系统最核心的判断之一。

### 4.1 判断公式

> **如果失败的影响是"这一次结果质量下降" → 降级**
> **如果失败的影响是"多实例状态不一致 / 数据损坏 / 安全边界破坏" → 阻断**

### 4.2 具体场景对照表

| 场景 | 行为 | 理由 |
|---|---|---|
| LLM 评估失败 | ✅ 降级（规则评分）| 评估质量下降但仍能完成 |
| LLM 选题失败 | ✅ 降级（规则选题）| 题目可能不那么贴合，但能继续 |
| RAG 检索失败 | ✅ 降级（fallback 题库）| 题目库变小，但仍有题 |
| **Redis snapshot 写失败** | ✅ 降级（记 `redis_snapshot`）| 本地 store 仍有 session；下次请求依赖本地 |
| **Event hub publish 失败** | ✅ 降级（计数 + log）| SSE 订阅者可能丢事件，但主流程不阻断；订阅者重连补齐 |
| **Redis Lease acquire/renew 失败** | ❌ 阻断（翻 409）| 关系到多实例所有权边界 |
| **PG migration 失败** | ❌ 阻断（启动 panic）| 数据 schema 不一致，继续运行会写脏数据 |
| **配置错误**（ErrPermanent）| ❌ 阻断 | API key 缺失、必填字段为空，重试无意义 |
| **Snapshot load 失败**（跨实例 takeover 路径）| ❌ 阻断 | 没 snapshot 就没法 takeover |

### 4.3 工程纪律

我把这个原则写进了 `CLAUDE.md` 的"不要做"清单：

```
不要做：
- 不要在节点里静默吞掉 LLM 错误；失败必须显式降级并写 `WorkingMemory.DegradedReasons`。
```

> **这一条不只是技术规则，是团队协作纪律。** 下次接手的人随手写一个 `if err != nil { return nil }` 就能让整个系统的可观测性崩盘。

## 五、报告侧汇总：让用户感知

### 5.1 Report.NextSteps 自动汇总

```go
// internal/nodes/report.go 节选
func Report(ctx context.Context, sess *domain.Session) error {
    report := buildReport(sess)

    // 关键：把降级组件汇总到 NextSteps
    if len(sess.WorkingMemory.DegradedReasons) > 0 {
        degradedComponents := collectDegradedComponents(sess)
        report.NextSteps = append(report.NextSteps, formatDegradationHint(degradedComponents))
    }

    sess.Report = report
    return nil
}

// collectDegradedComponents 按稳定顺序收集 component 名（排序保证可复现）
func collectDegradedComponents(sess *domain.Session) []string {
    components := make([]string, 0, len(sess.WorkingMemory.DegradedReasons))
    for component := range sess.WorkingMemory.DegradedReasons {
        components = append(components, component)
    }
    sort.Strings(components)
    return components
}

// formatDegradationHint 把 component 名翻译成人读文案
func formatDegradationHint(components []string) string {
    // "本次评估的 [评估, 选题, 检索] 环节出现降级，建议稍后重测以提高可信度"
    labels := make([]string, 0, len(components))
    for _, c := range components {
        labels = append(labels, componentLabel(c))
    }
    return fmt.Sprintf("本次评估的 [%s] 环节出现降级，建议稍后重测以提高可信度", strings.Join(labels, ", "))
}

// componentLabel 把稳定的 component 名映射成中文标签
func componentLabel(component string) string {
    switch component {
    case "pick":           return "选题"
    case "eval":           return "评估"
    case "critic":         return "深度判定"
    case "refine":         return "二次评估"
    case "probe":          return "追问"
    case "rag":            return "检索"
    case "redis_snapshot": return "状态持久化"
    default:               return component
    }
}
```

### 5.2 用户看到的报告

```markdown
# 面试复盘报告

## 综合评估
总分：72/100
覆盖技能：Goroutine、Channel、Map 并发

## 各题反馈
...

## 后续建议
- 加强 Goroutine 调度（GMP 模型）的学习
- 多刷 Channel 阻塞场景题
- **本次评估的 [评估, 选题] 环节出现降级，建议稍后重测以提高可信度**  ← 关键
```

> **用户能直接感知降级**，而不是默默拿到一个不靠谱的分数。

## 六、计数器维度（强类型 vs 弱类型）

### 6.1 早期弱类型（有问题）

```go
// 早期写法：Notes map 存计数
sess.WorkingMemory.Notes["scored_rounds"] = "5"
sess.WorkingMemory.Notes["degraded_rounds"] = "2"

// 读的时候要 strconv：
scored, _ := strconv.Atoi(sess.WorkingMemory.Notes["scored_rounds"])
```

**问题**：
- typo 不会编译报错（`scored_round` vs `scored_rounds`）
- 每次读都要 `strconv.Atoi`
- 测试很难写（要 mock map 内容）

### 6.2 演进后的强类型

```go
type WorkingMemory struct {
    // 强类型计数器
    ScoredRounds    int     // 已评估的轮次数
    DegradedRounds  int     // 降级评估的轮次数
    ReflectTopic    string  // reflection_check → pick_next 的补漏信号

    // 强类型降级表
    DegradedReasons map[string]string  // component → reason

    // 仅保留旧状态兼容（不再放主流程协议）
    Notes map[string]string
}
```

**好处**：
- 编译期类型检查
- 读写不需要类型转换
- 测试可以直接 `assert.Equal(t, 5, sess.WorkingMemory.ScoredRounds)`

### 6.3 兼容旧 session（Migration）

```go
// internal/domain/migration.go
func (s *Session) MigrateLegacyState() {
    if s == nil || s.WorkingMemory == nil {
        return
    }
    wm := s.WorkingMemory

    // 旧 scored_rounds → 新 ScoredRounds
    if wm.ScoredRounds == 0 && wm.Notes != nil {
        if v, ok := wm.Notes["scored_rounds"]; ok {
            if n, err := strconv.Atoi(v); err == nil {
                wm.ScoredRounds = n
            }
            delete(wm.Notes, "scored_rounds")  // 清理老 key
        }
    }

    // 旧 degraded_rounds → 新 DegradedRounds
    // ... 类似 ...

    // 旧 reflect_topic → 新 ReflectTopic
    if wm.ReflectTopic == "" && wm.Notes != nil {
        if v, ok := wm.Notes["reflect_topic"]; ok {
            wm.ReflectTopic = v
            delete(wm.Notes, "reflect_topic")
        }
    }

    // 旧 *_degraded → 新 DegradedReasons
    // ... 类似 ...
}
```

**关键设计**：

- `Graph.Invoke` 和 `Resume` **入口自动调用** Migration（不需要节点关心）
- Redis `LoadSnapshot` 也调用 Migration
- 部署中如果新旧版本共存，新版本读老 snapshot **透明转换**

```go
// graph.go
func (r *Runnable) Invoke(ctx context.Context, sess *domain.Session) error {
    sess.MigrateLegacyState()  // ← 自动
    return r.run(ctx, sess, []string{r.g.entry})
}

func (r *Runnable) Resume(ctx context.Context, sess *domain.Session) error {
    sess.MigrateLegacyState()  // ← 自动
    // ...
}
```

## 七、observability：可观测性 Callback

### 7.1 RecordingCallback

```go
// internal/observability/recording_callback.go
type RecordingCallback struct {
    mu      sync.Mutex
    records []NodeRecord
}

type NodeRecord struct {
    Node     string
    StartAt  time.Time
    EndAt    time.Time
    Duration time.Duration
    Error    string
    ErrType  string  // 分类（transient / permanent / schema / canceled）
}

func (r *RecordingCallback) OnNodeStart(ctx, node, sess) {
    r.mu.Lock()
    defer r.mu.Unlock()
    r.records = append(r.records, NodeRecord{Node: node, StartAt: time.Now()})
}

func (r *RecordingCallback) OnNodeEnd(ctx, node, sess) {
    r.update(node, "")
}

func (r *RecordingCallback) OnNodeError(ctx, node, sess, err) {
    r.update(node, classifyErr(err))
}
```

### 7.2 RecordingChatModel（最外装饰器）

```go
// internal/llm/recording.go
type RecordingChatModel struct {
    inner    ChatModel
    records  []CallRecord
}

type CallRecord struct {
    StartAt   time.Time
    Duration  time.Duration
    InputLen  int
    OutputLen int
    ErrType   string  // "" / "transient" / "permanent" / "schema" / "breaker_open" / "canceled"
}

func (m *RecordingChatModel) Generate(ctx, msgs, opts) (*Response, error) {
    start := time.Now()
    resp, err := m.inner.Generate(ctx, msgs, opts)
    m.record(CallRecord{
        StartAt:  start,
        Duration: time.Since(start),
        InputLen: sumLen(msgs),
        ErrType:  ClassifyChatErr(err),
    })
    return resp, err
}

// ClassifyChatErr 暴露给 demo / observability 共用
func ClassifyChatErr(err error) string {
    if err == nil { return "" }
    if errors.Is(err, ErrBreakerOpen)            { return "breaker_open" }
    if errors.Is(err, ErrSchemaInvalid)          { return "schema_invalid" }
    if errors.Is(err, ErrPermanent)              { return "permanent" }
    if errors.Is(err, context.Canceled)          { return "canceled" }
    if errors.Is(err, context.DeadlineExceeded)  { return "timeout" }
    if errors.Is(err, ErrTransient)              { return "transient" }
    return "unknown"
}
```

### 7.3 关键设计：必须放在 BreakingChatModel 外层

```go
// factory.go
return NewRecordingChatModel(
    NewBreakingChatModel(            // ← Recording 必须在 Breaker 外面
        NewLimitedChatModel(real, max),
        threshold, openDuration,
    ),
)
```

**为什么**：

- 需要记录 `ErrBreakerOpen` 和 `context.Canceled` 这种**被装饰器自己拦截的错误**
- 如果 Recording 在 Breaker 内，看到的永远是真实 LLM 的响应，**永远看不到 ErrBreakerOpen**
- 这种错也算"调用"，必须计入观测

## 九、可能的追问与回答

### Q：为什么不用 OpenTelemetry / Prometheus？

**A**：这是下一步要做的（已在 `HANDOFF.md` TODO）。当前用 `DegradedReasons` + slog 是最小可行实现，足够覆盖：
- 业务降级可见（汇总到报告）
- 开发期可见（slog 输出）
- demo 期可见（run.json）

加 OTel 是为了**生产期监控告警**，但要先有"统一的降级语义"才能加 metric 维度，所以**先做 DegradedReasons，再加 metric**。

### Q：降级原因放在 session 里会不会让 session 越来越大？

**A**：DegradedReasons 是 `map[string]string`，component 总共 ~10 个，reason 是短字符串。**单 session 增长上限 ~1KB**，可忽略。

### Q：如果一个 component 多次降级，原因会被覆盖吗？

**A**：会，**只保留最后一次**。这是有意的：
- 多次降级通常原因一样
- 历史 reason 已经在 LLM 调用 record 里（cmd/demo 的 run.json 完整保留）
- DegradedReasons 是"汇总表"，不是"历史日志"

### Q：怎么测试"降级路径"被正确触发？
