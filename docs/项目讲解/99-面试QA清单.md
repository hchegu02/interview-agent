## 🔥 Part 2：自研 Graph 框架（核心亮点 1）

### Q4. 你的 Graph 框架核心 API 是什么样的？为什么这么设计？★★★★★

**参考答案**：

> 核心抽象就两个：
>
> ```go
> type NodeFunc func(ctx context.Context, sess *domain.Session) error
> type Router  func(sess *domain.Session) string
> ```
>
> 设计取舍：
>
> 1. **NodeFunc 签名固定不带返回值** —— 所有状态都写在 `sess` 上，强制节点用领域模型通信而不是临时变量。
> 2. **Router 是纯函数** —— 架构规则强制 Router 禁止副作用，所有写 PendingDecision、Notes 的动作必须在节点里完成。这样 router 可以单测、可以重放、可以静态分析。
> 3. **挂起靠 ErrSuspended 哨兵** —— 节点 return `graph.ErrSuspended` 后 runtime 暂停，外部填好用户答案再 `Runnable.Resume(sess)`，从 `sess.CurrentNode` 下游继续。
> 4. **错误分类** —— `ErrPermanent` 终止整张图（如配置错误），普通错误正常返回让节点决定重试/降级。
>
> 整个 graph 包不到 500 行，**架构规则写进 `CLAUDE.md`：不要往 graph 包加业务逻辑，它只该懂"节点 / 边 / suspend"**。

### Q5. 为什么不用字节的 Eino 框架？★★★★

**参考答案**：

> 看过 Eino 源码，主要是两点考虑：
>
> 1. **挂起恢复语义不一样**：Eino 设计上是流式 LLM Pipeline，挂起恢复需要嵌套 Runnable + Callback，不适合"在任意节点等待外部 HTTP 答案"的场景；我的 ErrSuspended + CurrentNode 实现 ~50 行就够了。
> 2. **强约束更难做**：Eino 是开源框架，要兼顾各种场景，Router 可以有副作用。我自研可以**架构规则强制 Router 纯函数 + 节点错误分类 + WorkingMemory 强类型协议**，长期可维护性更好。
>
> 当然如果是团队协作或者多人项目，用 Eino 这种成熟框架更合适。**自研的前提是"框架边界小、规则清晰、用一辈子"**。

### Q6. Suspend/Resume 是怎么实现的？多次 Resume 会有什么问题吗？★★★★

**参考答案**：

> 实现机制：
> - 节点在等用户输入时 `return graph.ErrSuspended`
> - Runtime 检测到这个哨兵 → 把 `sess.CurrentNode` 设成当前节点 → 退出 Invoke 循环
> - 外部接到用户答案后写 `sess.Rounds[last].Answer`，调 `Runnable.Resume(sess)`
> - Resume 从 `sess.CurrentNode` 找到下游节点继续执行
>
> 多次 Resume 的隐患：
> 1. **重复 Resume**：客户端可能重试 Answer 接口，所以 Service 层用 Redis Lease 做幂等边界（同一 session 只有一个 owner 实例能 Resume）。
> 2. **Resume 前状态污染**：如果上次 Resume 中途 crash，sess 可能处于部分修改状态。解决方法是**节点要么完整成功、要么完全不写状态**（典型例子：先调 LLM 拿到 evaluation，再统一写入 sess）。
> 3. **跨实例 Resume**：见 Q9 跨实例 Takeover。

## 🚀 Part 3：多实例分布式协调（核心亮点 2，金山云最爱）

### Q7. 你说项目支持多实例，具体怎么做的？★★★★★

**参考答案**：

> 多实例需要解决三个问题，我每个都做了：
>
> 1. **Session 归属（Ownership）** → Redis Lease
>    - 每个 session 在 Redis 上有一个 lease key，记录当前 owner 实例 ID 和过期时间
>    - `acquire` 在 start 时获取；`renew` 在 answer 时续约；`release` 在 session 完成时释放
>
> 2. **跨实例状态共享** → Redis Snapshot
>    - 每次 start/answer 都把 session 序列化写到 Redis snapshot
>    - 另一实例本地 store miss 时，从 Redis snapshot 恢复
>
> 3. **冲突处理** → HTTP 409 + Retry-After + 服务端短重试
>    - 客户端请求落到 owner 不一致的实例时，返回 409 + `Retry-After: 1` + JSON `retry_after_seconds: 1`
>    - 服务端在 `acquireSessionLease` 内做 3 次指数退避（25→50→100ms）+ 半量抖动，吸收 lease 切换瞬时冲突
>    - 用尽再翻 `ErrSessionLeaseConflict`，客户端按 Retry-After 做长重试

### Q8. Lease 过期怎么处理？两个实例同时 acquire 怎么办？★★★★★

**参考答案**：

> Lease 过期场景分两种：
>
> 1. **Owner 实例正常 release**：lease key 直接删除，下次 acquire 谁先到谁拿。
> 2. **Owner 实例宕机**：lease 自然过期，**这时不能直接 acquire**——必须确认当前 lease key 已经过期或不存在才能写新的 owner，否则会和短暂复活的旧 owner 竞争。
>
> 我用 Redis 的 `SET key value NX EX seconds`：
> - `NX` 保证只在 key 不存在时写入（防止覆盖活跃的 lease）
> - `EX` 保证自动过期（防止 owner 永久占用）
> - 返回 OK 才算 acquire 成功，否则拿当前 owner 信息走 409 流程
>
> **同时 acquire 的竞争**：靠 Redis 单线程命令的天然原子性解决——两个实例同时 SET NX，只有一个会成功。

**面试官的钩子**：可能继续问 "为什么不用 Redlock" → 答："单 Redis 实例 + NX EX 已经够这个项目的 SLA；Redlock 适合多 Redis 节点强一致场景，会引入更多复杂度（时钟漂移、网络分区时的 majority quorum），ROI 不划算。"

### Q9. 跨实例 Takeover 的完整流程能讲一下吗？★★★★★

**参考答案**：

> 假设两个实例 A、B，session demo-1 原本由 A 持有：
>
> 1. **正常请求**（owner 实例）：
>    - 用户 answer 打到 A → A 检查本地 store 有 session → renew lease（续约成功）→ 推进 Graph → 写本地 store + Redis snapshot → 返回结果
>
> 2. **A 宕机后用户重连打到 B**：
>    - B 收到 answer 请求 → 本地 store miss
>    - B 调 Redis coordinator 查 lease → 发现 lease 过期（A 死了没续约）
>    - B 尝试 acquire lease → 成功（拿到 ownership）
>    - B 从 Redis snapshot 反序列化 session 装入本地 store
>    - B 推进 Graph、写本地 store + 新 snapshot、返回结果
>
> 3. **如果 A 没死只是网络抖动，A 后续答到的请求**：
>    - A 本地有 session，但 renew lease 失败（B 已经是新 owner）
>    - A 返回 409 + Retry-After
>    - 客户端重试，下次可能打到 B（已经接管）或 A 自己（A 本地 session 已经是脏的，必须从 Redis 重新 load）
>
> **关键边界**：Lease acquire/renew 失败**必须阻断主流程**（不能继续推进 Graph 写状态），因为这关系到多实例所有权。但 Redis snapshot 写失败可以**降级**（不阻断，只在 `DegradedReasons["redis_snapshot"]` 记录原因），因为下次请求会从本地 store 继续。

### Q10. 客户端 Retry-After 和服务端短重试为什么要两层？只做一层不行吗？★★★★

**参考答案**：

> 两层重试各管各的场景，缺一不可：
>
> 1. **服务端短重试**（3 次 25→50→100ms 指数退避 + 半量抖动）：吸收**瞬时 lease 切换冲突**——比如 lease 刚好在请求处理过程中过期，旧 owner 释放和新 acquire 之间有微秒级窗口。这种冲突应该在服务端透明吸收，不应该让客户端感知。总耗时上限 250ms，控制在用户感知阈值内。
>
> 2. **客户端长重试**（HTTP 409 + Retry-After: 1）：处理**真正的所有权转移**——比如某个 session 已经被另一个实例确定接管了，本实例就是没 ownership。这种情况服务端短重试再多次也没用，只能让客户端去找正确的实例。
>
> 如果只做客户端重试：用户体验差（每次瞬时冲突都要等 1 秒+ DNS 解析 + TCP 握手）。
> 如果只做服务端重试：长时间持锁会让其他请求堆积，不如让客户端自己 backoff。
>
> 这个设计是参考了 etcd、TiKV 这种分布式存储系统的"两层重试"模式。

## 🛡️ Part 4：三层防护体系（核心亮点 3）

### Q11. 三层防护的链路是什么？为什么是这个顺序？★★★★★

**参考答案**：

> 链路从外到内：
>
> ```
> HTTP Request
>     ↓
> [1] MaxInFlightMiddleware  (HTTP 入口背压，超限返 503)
>     ↓
> InterviewService
>     ↓
> [2] BreakingChatModel      (熔断器，open 时直接 ErrBreakerOpen)
>     ↓
> [3] LimitedChatModel       (进程内并发 limiter，max_concurrency=4)
>     ↓
> RealChatModel (调外部 LLM)
> ```
>
> 顺序原因：
>
> - **背压在最外**：HTTP 入口就拦截过载请求，避免请求堆积消耗下游资源。
> - **熔断在 Limiter 外面**：如果反过来（Limiter 包 Breaker），熔断 open 时还要先等 limiter 槽位，浪费容量。**熔断 open 应该零成本短路返回。**
> - **Limiter 紧挨着 Real**：保护真正的稀缺资源（外部 LLM 调用名额），其他装饰器都不应该消耗这个名额。

### Q12. 熔断器为什么只统计部分错误？★★★★★

**参考答案**：

> 我的熔断器只统计 `ErrTransient` 和 `context.DeadlineExceeded`，**显式不统计** `context.Canceled` / `ErrPermanent` / `ErrSchemaInvalid`。
>
> 原因：
>
> 1. **`context.Canceled`** —— 客户端主动断开连接（比如关页面），不是 LLM 的问题。如果统计，会出现"用户大量取消请求 → 熔断器误触发 → 真实请求被熔断"的级联故障。
>
> 2. **`ErrPermanent`** —— 比如 API key 错误、prompt 格式错误。这种错误重试 100 次也不会好，熔断器关掉它对修复没帮助；而且这类错误通常很快返回，会"刷分"让熔断器一直 closed。
>
> 3. **`ErrSchemaInvalid`** —— LLM 返回了不符合 JSON schema 的内容。这是 prompt 工程问题，不是 LLM 服务可用性问题。
>
> 4. **统计的两类**：
>    - `ErrTransient` —— 真实的临时故障（5xx、连接超时、限流）
>    - `DeadlineExceeded` —— 整体请求超时（可能是 LLM 慢，也可能是网络抖）
>
> 这种**"错误分类驱动的熔断策略"**比 Hystrix 默认的"所有 Exception 都算"更精准，避免误触发。

### Q13. 熔断 open 时为什么返回 ErrBreakerOpen 而不是 ErrTransient？★★★★

**参考答案**：

> 这是个**接口契约设计**问题。
>
> 如果熔断 open 时返回 `ErrTransient`，上游调用者（比如节点里的 LLM 调用代码）会误以为这是临时故障 → 触发**节点级重试** → 但下次调用还是会被熔断 → 反复无效重试。
>
> 所以我专门定义了一个**新哨兵 `ErrBreakerOpen`**：
>
> - 上游识别到 `ErrBreakerOpen` → 走**降级 fallback 路径**（比如规则评分 / 默认题目）
> - 不会触发任何重试
> - `WorkingMemory.DegradedReasons[component] = "breaker_open"` 显式记录
>
> 半开期只允许 1 个 probe 请求通过，避免半开瞬间大量并发把还没恢复的下游又打挂。

---

### Q14. HTTP 背压为什么只挂在 /start 和 /answer，不挂全局？★★★★

**参考答案**：

> 三类路由各有不同特点：
>
> 1. **`/healthz` `/readyz`** —— k8s 的存活/就绪探针，**必须永远响应**。如果背压拦截健康检查，pod 会被误判挂掉重启。
>
> 2. **`/api/interview/stream`** —— SSE 长连接，**生命周期是分钟级甚至更久**。如果用同一个 buffered chan 计数，长连接占满了 chan 短请求就全挂了。stream 应该用**独立的连接数计数器**（这是我现在的 TODO）。
>
> 3. **`/start` `/answer`** —— 短连接请求，每个请求都会触发 Graph 推进和 LLM 调用，是真正吃资源的路径。**只对这两个路由做背压**，超限返回 503 + `Retry-After: 1` + JSON `retry_after_seconds: 1`，与 lease 冲突的 409 协议保持一致。
>
> 背压用 buffered chan 做**非阻塞 try-acquire**（不是 select with timeout），保证背压本身不消耗服务端资源。

---

### Q15. readyz 在熔断 open 时为什么返回 200 degraded 而不是 503？★★★★★

**参考答案**：

> 这是一个经典的"**就绪状态≠服务可用**"的判断。
>
> 我的逻辑：熔断 open 时 `/readyz` 返回 `200 + {"status":"degraded","llm_breaker":"open"}`。
>
> 原因：
>
> 1. **k8s readiness probe 返回非 200 会把 pod 从 Service 拉走** —— 但我的节点设计就支持"LLM 不可用时走规则降级路径"，pod 仍然能处理请求（只是质量下降）。把 pod 拉走反而损失可用容量。
>
> 2. **降级 ≠ 不可用** —— 用户拿到的可能是规则评分而不是 LLM 评分，但仍然能完成面试流程；如果整个 pod 被踢，用户连 fallback 路径都走不到。
>
> 3. **degraded 状态需要被监控** —— 我返回的 JSON 里带 `llm_breaker:"open"`，监控系统会告警，但流量正常分发。
>
> 类比：Netflix 的 Hystrix dashboard 也是这种思路——熔断打开不代表服务挂了，代表服务正在"保护性降级"。
>
> 真正会返 503 的场景：**lease acquire 失败、PG 连不上等"真的没法处理请求"的情况**。

## 📊 Part 5：显式降级与可观测性（核心亮点 4）

### Q16. 你说的"显式降级"具体是什么？★★★★★

**参考答案**：

> 工程纪律层面我有一条铁律：**不静默吞错**。
>
> 具体实现：每个节点遇到 LLM 失败 / 外部依赖失败时，**必须**：
>
> 1. 走规则 fallback 路径（节点内的 `ruleBasedXxx` 函数）继续推进流程
> 2. **显式写入** `WorkingMemory.DegradedReasons[component] = reason`
>    - component 用稳定名（`pick`/`eval`/`rag`/`redis_snapshot`/`breaker_open`...）
>    - reason 是人读的原因（错误信息或降级类型）
>
> 这样做的好处：
>
> - **可观测**：报告里 `Report.NextSteps` 自动汇总降级组件，提示用户"评估时 X 环节降级了，建议重测以提高可信度"
> - **可恢复**：日志和监控能立刻定位是哪一层降级了
> - **可测试**：单测可以验证"LLM 失败时是否进入 fallback + 是否正确写入 DegradedReasons"
>
> 对比错误做法：很多项目用 `if err != nil { log.Println(err); return defaultValue }`，这种代码上线后**bug 永远查不到**。

---

### Q17. 哪些场景可以降级，哪些必须阻断？★★★★★

**参考答案**：

> 我的判断原则：**"降级会不会破坏正确性边界"**。
>
> **可以降级（不阻断主流程）**：
> - LLM 调用失败 → 走规则 fallback（评估质量下降但仍能完成）
> - RAG 检索失败 → 走 fallback question bank（题目质量下降但仍有题）
> - **Redis snapshot 写失败** → 只记 `DegradedReasons["redis_snapshot"]`，下次请求依赖本地 store + PG 恢复
> - Event hub publish 失败 → SSE 订阅者可能丢事件，但主流程不阻断
>
> **必须阻断**：
> - **Redis lease acquire/renew 失败** —— 关系到多实例所有权边界，继续推进会出现两个实例同时改一个 session
> - **配置错误**（`ErrPermanent`）—— 比如 API key 缺失、必填字段为空，重试无意义
> - **PG migration 失败** —— 数据 schema 不一致，继续运行会写脏数据
>
> **判断公式**：
> - 如果失败的影响是"**这一次结果质量下降**" → 降级
> - 如果失败的影响是"**多实例状态不一致 / 数据损坏 / 安全边界破坏**" → 阻断

### Q18. WorkingMemory 从 Notes map 演进到强类型字段，具体怎么做的？★★★

**参考答案**：

> 早期 `WorkingMemory` 用 `Notes map[string]string` 传跨节点状态：
>
> ```go
> // 早期写法（有问题）

> sess.WorkingMemory.Notes["reflect_topic"] = "并发安全"

## 🔍 Part 6：RAG / LLM 输出稳定性（亮点 5）

### Q19. RAG 怎么做的？为什么不直接调向量库？★★★★

**参考答案**：

> 单纯向量检索的问题：语义相近但**领域不对**的题会被召回（比如 JD 是 Go 后端，召回了 Python 后端的题）。
>
> 我的方案是 **PG 端两路召回 + Go 端三路融合**：
>
> 1. **PG 端两路并行**：
>    - **Vector candidates**：基于 embedding 余弦相似度
>    - **Tag candidates**：基于 JD 提取的 tag 字段精确匹配
>
> 2. **Go 端 LinearFusion 三路评分融合**：
>    ```
>    final_score = w1 * vector_score + w2 * topic_score + w3 * difficulty_score
>    ```
>    - vector_score：原始余弦相似度
>    - topic_score：tag 命中率
>    - difficulty_score：题目难度与 GapReport 推荐难度的接近度
>
> 3. **离线 reindex 与在线服务解耦**：`cmd/reindex` 是独立 CLI，重建 embedding 不影响在线服务。
>
> 4. **启动时强校验**：Embedder 输出维度必须和 PG `vector(N)` 一致，配置错了启动就失败（`ErrPermanent`），不会运行时报怪错。

### Q20. LLM 返回的 JSON 格式不稳怎么办？★★★★

**参考答案**：

> 我封装了 `llm.CallWithSchema(ctx, model, messages, opts, validator, maxFixAttempts)`：
>
> 1. **设 ResponseFormat = json_object**（OpenAI 兼容 API 的标准方式）
> 2. **每个节点提供手写 validator** 函数（不用 reflection，性能好且类型安全）
> 3. **校验失败时把错误反馈给 LLM 让它自纠**：
>    ```
>    第二次 prompt = 原 prompt + LLM 上次回答 + "解析错误：缺字段 X，请只返回 JSON"
>    ```
> 4. **maxFixAttempts 用尽后翻 `ErrSchemaInvalid`**（不算熔断错误，见 Q12）
>
> 5. **每次 attempt 都发 slog 事件**：
>    - `event=llm_schema_attempt`（debug 级）
>    - `event=llm_schema_validation_failed`（info 级，含 error detail）
>
> 这样 demo 报告里可以统计 `schema_retries` 次数，作为 prompt 稳定性的指标。

## 🌊 Part 7：SSE 流式与并发（亮点 6）

### Q21. SSE 的 Last-Event-ID 怎么实现的？★★★

**参考答案**：

> 客户端断线重连时会带 `Last-Event-ID` HTTP header（或 query 参数 `last_event_id`），表示"上次收到的最后一个事件 ID"。
>
> 我的实现：
>
> 1. **内存 event hub 保留近期事件历史**（环形 buffer）
> 2. 新订阅者 Subscribe 时：
>    - 如果带 Last-Event-ID → 回放该 ID 之后的所有历史事件
>    - 不带 → 只发当前 snapshot，等新事件
> 3. **关键顺序**：回放历史必须**在注册 live subscriber 之前完成**，否则 live 事件可能插到 replay 前面，破坏事件顺序。
>
> 我还做了两个细节：
>
> - **事件里的 question/report 字段深拷贝**：避免历史事件被后续 session 变更污染（早期 bug：因为是引用语义，重连后看到的 question 其实是当前最新题不是当时的题）
> - **heartbeat `: ping`**：SSE 协议中以 `:` 开头的行是注释（不算事件），用于防止代理（Nginx/Cloudflare）把空闲连接断掉

---

### Q22. SSE 修了哪些并发 race？★★★★

**参考答案**：

> 修过两个：
>
> **Race 1：Subscribe → Publish 之间 readLoop 未进入 XREAD $**
>
> Redis Streams 的 `XREAD $` 表示"从订阅时刻之后的最新位置开始读"。
>
> 原来的 bug：
> ```
> 1. Subscribe(stream, "") 返回（但 readLoop 还没真正进入 XREAD $）
> 2. 测试代码立刻 Publish(event)
> 3. readLoop 在事件发完后才进入 XREAD $，错过这个事件
> ```
>
> 修复：`Subscribe` 改成**同步打开 Redis 连接并读取 stream 当前最新 ID**，之后才返回。后续 readLoop 用这个 ID 做 `XREAD` 起点，保证不会错过事件。
>
> **Race 2：Publish 与 Close 并发**
>
> 原来的 bug：
> ```
> 1. Publish 在循环里向各 subscriber channel 发送事件
> 2. 同时另一 goroutine 调 Close，关闭所有 subscriber channel
> 3. Publish 可能向已 close 的 channel 发送 → panic
> ```
>
> 修复：
> - Publish 的 channel send 必须在 hub 锁内完成
> - Close 也要拿同一把锁
> - 这样 send 和 close 不会交叉
>
> 这两个 race 都是**实际跑集成测试遇到的**，写完单测加 `-race` 才暴露。

### Q23. Mock/Real 双模式怎么设计的？★★★

**参考答案**：

> 核心思路：**所有外部依赖都抽象成接口，单测注入 mock，集成测试注入 real**。

> 抽象层：
>
> ```go
> // LLM
> type ChatModel interface { Chat(ctx, msgs, opts) (*Response, error) }
> // 实现：RealChatModel / MockChatModel / stubChatModel
>
> // Embedder
> type Embedder interface { Embed(ctx, texts) ([][]float32, error) }
>
> // Retriever

## 🧠 Part 9：领域设计与取舍

### Q26. Score = -1 这个设计是什么意思？★★★

**参考答案**：

> Go 没有 nullable int，需要显式区分两种情况：
>
> - **Score = 0**：答得很差（满分 100，确实是零分）
> - **Score = -1**：评估失败（LLM 调用失败 / Schema 校验失败 / 降级路径未给分）
>
> 如果统一用 0，统计 AvgScore 会把"未评估"算成"零分"，污染整体打分。
>
> 我的规则：**所有统计逻辑（AvgScore、SkillCoverage 累加等）必须先判 `Score < 0` 跳过**。
>
> 这个不是最优设计——更优是 `Evaluation *EvaluationStatus` 用 nil 表示未评估，但改起来牵连测试太多，我把它列为后续重构 TODO（在 `HANDOFF.md` 的风险表里）。
>
> **能意识到当前设计不是最优 + 有重构计划**，这本身也是面试加分项。

### Q27. FinalEvaluation() 这个方法是干什么的？★★

**参考答案**：

> 每个 AnswerRound 有 `Evaluation`（初评）和可选 `RefinedEval`（Critic-Refine 二次反思的修正评）。
>
> 早期下游代码直接读 `round.Evaluation`，漏掉 refine 结果。
>
> 我加了：
>
> ```go
> func (r *AnswerRound) FinalEvaluation() *Evaluation {
>     if r.RefinedEval != nil { return r.RefinedEval }
>     return r.Evaluation
> }
> ```
>
> 然后**架构规则强制**：**禁止直接读 `Evaluation` 做最终聚合，必须用 `FinalEvaluation()`**（写进 CLAUDE.md）。
>
> 这是一个典型的"**用方法封装业务规则**"的例子——把"什么是最终评估"这个语义集中在一个地方，下游不用记规则。

**回答**：

> 选 Redis 的理由：
> - 项目已经依赖 Redis 做 event hub，避免引入新组件
> - Etcd lease 的 KeepAlive 长连接对客户端复杂度更高
> - Redis NX EX + 短租约 + 续约 + 应用层 409 重试，已经能 cover 90% 场景
