# 亮点 2：多实例分布式协调（Redis Lease + Snapshot + Takeover）

> 代码位置：`internal/httpapi/redis_session_coordinator.go`、`interview.go` 的 `acquireSessionLease` / `retryAcquireLease`
> 关键能力：跨实例 Takeover、Lease 冲突处理、Snapshot 降级、Owner 边界保护
> 面试官追问命中率：★★★★★（分布式应用平台岗位最关心）

---

## TL;DR（30 秒讲清楚版）

> 项目支持**水平扩展多实例部署**，靠 Redis 解决三个核心问题：
> 1. **Session 归属**：每个 session 通过 `SET NX PX` 拿到唯一 owner lease
> 2. **跨实例状态共享**：每次 start/answer 把 session JSON 写到 Redis snapshot（带 TTL）
> 3. **故障 Takeover**：owner 宕机后，另一实例从 snapshot 恢复 session 并 acquire 新 lease 接续 answer
>
> Lease 冲突的双层重试：**服务端短重试（3 次指数退避 + 半量抖动，上限 250ms）** 吸收瞬时切换冲突，**客户端长重试（HTTP 409 + Retry-After: 1）** 处理真正的所有权转移。
>
> 关键工程纪律：**Lease acquire/renew 失败必须阻断**（多实例所有权边界），**Snapshot 写失败可以降级**（不阻断主流程，只记 `DegradedReasons["redis_snapshot"]`）。

## 一、为什么需要

### 1.1 单实例的痛点

最初的实现是 **HTTP server + 内存 session map**：

```go
type InterviewService struct {
    runner interviewRunner
    store  map[string]*Session  // 内存
}
```

问题：
- ❌ 重启就丢所有进行中的面试
- ❌ 没法水平扩展（用户的请求必须打到同一台实例）
- ❌ 没法做灰度发布（滚动重启会切走 session）

### 1.2 加 PG 持久化解决了一半

```go
// PG sessions.state_json 持久化
type pgSessionStore struct { pool *pgxpool.Pool }
```

PG 解决了"重启不丢"，但**没解决多实例**：

| 场景 | 用 PG 后 | 问题 |
|---|---|---|
| 同一 session 同时打到两个实例 | 都能从 PG load | **两实例同时改一个 session → 数据冲突** |
| 实例 A 宕机，请求打到 B | B 能 load | **A 的 in-flight 请求可能再次写 PG → 脏数据** |

**根本原因**：PG 解决了"状态持久化"，但没解决"**谁有权改这个 session**"——这是分布式系统的 **Ownership 问题**。

## 二、整体设计（三件套）

```
                  ┌────────────────────────┐
                  │   Redis (单实例 or AOF)  │
                  └─────────┬──────────────┘
                            │
       ┌────────────────────┼────────────────────┐
       │                    │                    │
   Lease Key           Snapshot Key         Streams (事件总线)
   ───────────         ─────────────        ─────────────────
   key:   lease:demo-1    snapshot:demo-1   stream:demo-1
   value: "instance-A"    {session JSON...}  [event1, event2, ...]
   TTL:   30s             24h                自然过期
```

**三个 Key 各管各的**：

| Key | 解决什么 | 操作 | TTL |
|---|---|---|---|
| **Lease** | Ownership（谁能改）| `SET NX PX` / Lua-renew / Lua-release | 30s（短）|
| **Snapshot** | 状态共享（跨实例恢复）| `SET PX` JSON / `GET` / `DEL` | 24h（长，覆盖人类反应时间）|
| **Streams** | 事件分发（SSE 跨实例）| `XADD` / `XREAD` | 自然过期 |

## 三、Lease 实现细节（最关键的部分）

### 3.1 为什么选 Redis SET NX EX 而不是 Redlock / etcd

| 方案 | 一致性 | 复杂度 | 适用 | 我的取舍 |
|---|---|---|---|---|
| **Redis SET NX EX**（单实例）| Redis 单线程命令的原子性 | 极低 | 个人/小团队项目 | ✅ 选这个 |
| **Redlock**（多 Redis 节点 majority）| 强一致，但有时钟漂移争议 | 高 | 跨地域强一致场景 | 项目 SLA 不需要 |
| **etcd / ZooKeeper** | 强一致（Raft / ZAB）| 高（要部署集群）| 生产级金融 | ROI 不划算 |

**取舍逻辑**：

> 项目已经依赖 Redis 做 event hub，**避免引入新组件**。SET NX EX 对"个人面试场景"的 SLA 完全够用——即使丢一个 lease，最多影响一个用户的一次面试，可以重新开始。

**架构上 SessionCoordinator 是接口**：

```go
type SessionCoordinator interface {
    SaveSnapshot(ctx context.Context, sess *domain.Session, ttl time.Duration) error
    LoadSnapshot(ctx context.Context, sessionID string) (*domain.Session, error)
    AcquireLease(ctx context.Context, sessionID, ownerID string, ttl time.Duration) (bool, error)
    RenewLease(ctx context.Context, sessionID, ownerID string, ttl time.Duration) (bool, error)
    ReleaseLease(ctx context.Context, sessionID, ownerID string) (bool, error)
}
```

未来要换 etcd 实现只需要换 Coordinator 一处，业务无感知。

### 3.2 Acquire：靠 NX 防覆盖

```go
func (c *RedisSessionCoordinator) AcquireLease(ctx context.Context, sessionID, ownerID string, ttl time.Duration) (bool, error) {
    if err := validateLeaseInput(sessionID, ownerID, ttl); err != nil {
        return false, err
    }
    conn, err := c.open(ctx)
    if err != nil {
        return false, err
    }
    defer conn.Close()

    // SET key value NX PX milliseconds
    //   - NX 只在 key 不存在时写入 → 防止覆盖活跃 owner
    //   - PX 自动过期 → 防止 owner 永久占用
    value, err := redisDo(conn, "SET",
        c.leaseKey(sessionID),
        ownerID,
        "NX",
        "PX", strconv.FormatInt(ttl.Milliseconds(), 10))
    if err != nil {
        return false, fmt.Errorf("acquire session lease: %w", err)
    }
    return value == "OK", nil
}
```

**两个细节**：

1. **NX 保证只有第一个 acquire 成功**：两个实例同时 SET，Redis 单线程命令串行化，只有一个返回 OK。
2. **PX 是毫秒级 TTL**：用毫秒比秒更精细，因为 lease TTL 默认 30s，但 acquire 失败重试是毫秒级。

### 3.3 Renew：靠 Lua 保证"只续约自己拥有的 lease"

```go
// 旧版本错误写法（有 race）：
//   GET key → if value == ownerID → PEXPIRE key new_ttl
//   两个命令之间 lease 可能被别人 acquire，导致延长了别人的 lease

// 正确写法：用 Lua 在 Redis 端原子执行
const renewLeaseScript = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
    return 0
end`

func (c *RedisSessionCoordinator) RenewLease(ctx, sessionID, ownerID, ttl) (bool, error) {
    return c.evalOwnerScript(ctx, sessionID, ownerID, renewLeaseScript,
        strconv.FormatInt(ttl.Milliseconds(), 10))
}
```

**核心：用 Lua 让"check + 延长"成原子操作**，避免 TOCTOU（Time Of Check Time Of Use）race。

### 3.4 Release：同样用 Lua

```go
const releaseLeaseScript = `
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end`
```

为什么 release 也要校验 ownerID：
- 如果实例 A 的请求处理慢，lease 到期后实例 B 已经 acquire 了新 lease
- 这时 A 的请求完成调 release，**不能删 B 的 lease**
- Lua 脚本保证只有 owner 才能 release

### 3.5 RenewLease 失败时的优雅降级

```go
func (s *InterviewService) renewSessionLease(ctx context.Context, sessionID string) error {
    if s == nil || s.coordinator == nil {
        return nil
    }
    ok, err := s.coordinator.RenewLease(ctx, sessionID, s.ownerID, s.leaseTTL)
    if err != nil {
        return err
    }
    if ok {
        return nil
    }
    // Renew 失败有两种情况：
    //   1. Lease 已过期被 Redis 自动删除（key 不存在 → Lua 返回 0）
    //   2. 别的实例已经 acquire（GET 出来的 value 不是自己）
    // 第 1 种情况：尝试重新 acquire（如果其他实例还没抢就成功）
    // 第 2 种情况：acquire 也会失败 → 走 ErrSessionLeaseConflict
    return s.acquireSessionLease(ctx, sessionID)
}
```

**这是一个常被遗漏的细节**：

- Lease 过期不一定代表实例宕机，可能就是 GC 暂停一下、网络抖一下
- 给自己一次重新 acquire 的机会，不要直接报错让用户重新连
- 如果真被别人抢了，再翻 409

## 四、Snapshot：跨实例状态共享

### 4.1 写 Snapshot

```go
func (c *RedisSessionCoordinator) SaveSnapshot(ctx context.Context, sess *domain.Session, ttl time.Duration) error {
    raw, err := json.Marshal(sess)                          // 整个 session 序列化为 JSON
    if err != nil {
        return fmt.Errorf("marshal session snapshot: %w", err)
    }
    conn, err := c.open(ctx)
    if err != nil {
        return err
    }
    defer conn.Close()
    _, err = redisDoString(conn, "SET",
        c.snapshotKey(sess.ID),
        string(raw),
        "PX", strconv.FormatInt(ttl.Milliseconds(), 10))
    return err
}
```

**取舍**：

| 序列化方式 | 优点 | 缺点 | 我选 |
|---|---|---|---|
| JSON | 可读、跨语言 | 体积大 | ✅ 项目规模够小，可读性优先 |
| Protobuf | 体积小、性能好 | 需要 .proto schema | 流量大时切换 |
| Gob | Go 原生 | 不跨语言 | 不考虑 |

### 4.2 读 Snapshot + 自动迁移

```go
func (c *RedisSessionCoordinator) LoadSnapshot(ctx context.Context, sessionID string) (*domain.Session, error) {
    conn, err := c.open(ctx)
    if err != nil {
        return nil, err
    }
    defer conn.Close()
    value, err := redisDo(conn, "GET", c.snapshotKey(sessionID))
    if err != nil {
        return nil, fmt.Errorf("load session snapshot: %w", err)
    }
    raw, ok := value.(string)
    if !ok || raw == "" {
        return nil, fmt.Errorf("session snapshot %q not found", sessionID)
    }
    var sess domain.Session
    if err := json.Unmarshal([]byte(raw), &sess); err != nil {
        return nil, fmt.Errorf("unmarshal session snapshot: %w", err)
    }
    // 关键：兼容老版本 session 状态
    sess.MigrateLegacyState()
    return &sess, nil
}
```

**`MigrateLegacyState()` 是关键**：

- 部署中可能存在新旧两版本实例共存
- 老实例写的 snapshot 里 `Notes["scored_rounds"]` 是 string，新实例需要 `ScoredRounds` 是 int
- LoadSnapshot 自动调用 Migration，**新版本读老 snapshot 透明转换**

这是一个 **向后兼容的工程纪律**。

### 4.3 Snapshot 失败的优雅降级

```go
func (s *InterviewService) saveSessionSnapshot(ctx context.Context, sess *domain.Session) bool {
    if s == nil || s.coordinator == nil {
        return false
    }
    if err := s.coordinator.SaveSnapshot(ctx, sess, s.snapshotTTL); err != nil {
        // Snapshot 写失败不阻断主流程
        // 1. 本地 store 仍然有 session（内存或 PG）
        // 2. 下次请求如果还打到本实例可以正常恢复
        // 3. 但如果实例宕机，这个 session 就丢了 → 报告里提示用户复测
        markSessionDegraded(sess, "redis_snapshot", err.Error())
        return true   // 返回 true 表示"已记录降级原因"
    }
    return false
}

func markSessionDegraded(sess *domain.Session, component, reason string) {
    if sess.WorkingMemory.DegradedReasons == nil {
        sess.WorkingMemory.DegradedReasons = map[string]string{}
    }
    sess.WorkingMemory.DegradedReasons[component] = reason
}
```

## 五、Takeover 完整流程

### 5.1 场景：实例 A 宕机，用户重连打到实例 B

```
T0:  User start → 打到 A → A acquire lease → A 写本地 store + Redis snapshot
T1:  User answer Q1 → 打到 A → A renew lease → A 推进 graph → 更新本地 + snapshot
T2:  实例 A crash 💥
T3:  Lease 自然过期（30s 后）
T4:  User answer Q2 → 重连打到 B
     - B 本地 store miss
     - B 调 coordinator.AcquireLease → 成功（key 已过期）
     - B 调 coordinator.LoadSnapshot → 从 Redis 拿到 session JSON
     - B 反序列化 + MigrateLegacyState → 装入本地 store
     - B 推进 graph + 写新 snapshot + renew lease
     - 返回 answer 结果
```

### 5.2 关键代码

```go
// getSessionForMutation：写路径专用，会尝试从 Redis snapshot 恢复
func (s *InterviewService) getSessionForMutation(ctx context.Context, sessionID string) (*domain.Session, error) {
    if s.store == nil {
        return nil, fmt.Errorf("%w: session store not configured", graph.ErrInvalidConfig)
    }
    sess, err := s.store.Get(ctx, sessionID)
    if err == nil {
        return sess, nil          // 本地 store 命中，直接用
    }
    if !errors.Is(err, ErrSessionNotFound) || s.coordinator == nil {
        return nil, err
    }
    // 本地 miss + 有 coordinator → 尝试从 Redis snapshot 恢复
    return s.coordinator.LoadSnapshot(ctx, sessionID)
}

// Get：读路径专用，恢复后会回写到本地 store 加速后续读
func (s *InterviewService) Get(ctx context.Context, sessionID string) (*domain.Session, error) {
    sess, err := s.store.Get(ctx, sessionID)
    if err == nil {
        return sess, nil
    }
    if !errors.Is(err, ErrSessionNotFound) || s.coordinator == nil {
        return nil, err
    }
    sess, err = s.coordinator.LoadSnapshot(ctx, sessionID)
    if err != nil {
        return nil, err
    }
    // 恢复到本地 store，下次读直接命中
    if err := s.store.Save(ctx, sess); err != nil {
        return nil, err
    }
    return sess, nil
}
```

**两个细节**：

1. **读路径回写本地 store**：避免每次读都打 Redis（典型的 read-through cache 模式）
2. **写路径不回写本地 store**：因为 Answer 路径要走 Lease acquire + 推进 graph，回写让主流程更清晰

## 六、双层重试：服务端短重试 + 客户端长重试

### 6.1 为什么要两层

考虑这个场景：

```
T0:  Lease 30s 即将过期（剩 10ms）
T1:  实例 A 收到 answer 请求
T2:  A 尝试 renew → Lua 返回 0（lease 已经过期被 Redis 删了）
T3:  A 尝试 acquire → 但实例 B 的探测请求刚好赢了赛跑（先 SET NX 成功）
T4:  A 的 acquire 返回 false → 翻 409 → 客户端等 1 秒重试
T5:  客户端重试打到 A 或 B → 看运气
```

**问题**：T2-T4 这个窗口只有几十毫秒，让客户端等 1 秒重试体验差。

### 6.2 服务端短重试：吸收瞬时冲突

```go
const (
    sessionLeaseAcquireMaxAttempts = 3
    sessionLeaseAcquireBaseBackoff = 25 * time.Millisecond
    sessionLeaseAcquireMaxBackoff  = 100 * time.Millisecond
    sessionLeaseAcquireDeadline    = 250 * time.Millisecond  // 总耗时上限
)

func (s *InterviewService) retryAcquireLease(ctx context.Context, attempt func(context.Context) (bool, error)) (bool, error) {
    start := time.Now()
    delay := sessionLeaseAcquireBaseBackoff

    for i := 0; i < sessionLeaseAcquireMaxAttempts; i++ {
        if err := ctx.Err(); err != nil {
            return false, err
        }
        ok, err := attempt(ctx)
        if err != nil {
            // 真错误（network、auth 等）立刻冒泡，不重试
            return false, err
        }
        if ok {
            return true, nil
        }
        if i == sessionLeaseAcquireMaxAttempts-1 {
            break
        }

        sleep := jitteredBackoff(delay)
        // 关键：如果下一个 sleep 会超过总预算就停下
        if time.Since(start)+sleep > sessionLeaseAcquireDeadline {
            break
        }
        timer := time.NewTimer(sleep)
        select {
        case <-ctx.Done():
            timer.Stop()
            return false, ctx.Err()
        case <-timer.C:
        }

        delay *= 2
        if delay > sessionLeaseAcquireMaxBackoff {
            delay = sessionLeaseAcquireMaxBackoff
        }
    }
    return false, nil
}
```

**核心设计点**：

| 设计 | 数值 | 原因 |
|---|---|---|
| `MaxAttempts = 3` | 3 次 | 经验值，覆盖 90% 的瞬时冲突 |
| `BaseBackoff = 25ms` | 25ms | 首次重试要快，避免短窗口冲突没等到 |
| `MaxBackoff = 100ms` | 100ms | 上限不能太长（否则连接占用） |
| `Deadline = 250ms` | 250ms | 总耗时上限，超过用户能感知 |
| **半量抖动** | `[d/2, d)` | 避免多实例同步雪崩 |
| **真错误立刻冒泡** | 不重试 | network/auth 错重试无意义 |
| **ctx 取消立刻退出** | `<-ctx.Done()` | 不能 sleep 到天荒地老 |
| **下一个 sleep 超预算就停** | `time.Since(start)+sleep > deadline` | 避免最后一次 sleep 撑爆总时间 |

### 6.3 半量抖动（Full Jitter）

```go
// jitteredBackoff 返回 [d/2, d) 之间的随机 sleep 时长
// full-jitter 风格能在多实例并发冲突时把重试时刻打散，避免雪崩同步
func jitteredBackoff(d time.Duration) time.Duration {
    if d <= 0 {
        return 0
    }
    half := int64(d / 2)
    if half <= 0 {
        return d
    }
    return time.Duration(half) + time.Duration(rand.Int63n(half))
}
```

**为什么不用 AWS 推荐的 full jitter `[0, d)`**：

- 0 可能让"压根没等"，瞬时冲突没缓解
- `[d/2, d)` 保证至少有 d/2 间隔，又有抖动，是 trade-off

参考资料：[AWS Architecture Blog - Exponential Backoff and Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)

### 6.4 客户端长重试：HTTP 409 + Retry-After

```go
func writeInterviewError(c *gin.Context, err error) {
    if errors.Is(err, ErrSessionLeaseConflict) {
        retryAfterSeconds := int(sessionLeaseRetryAfter.Seconds())
        c.Header("Retry-After", strconv.Itoa(retryAfterSeconds))
        c.AbortWithStatusJSON(http.StatusConflict, gin.H{
            "error":               "session lease conflict",
            "retry_after_seconds": retryAfterSeconds,
        })
        return
    }
    // ...
}
```

**两套协议保持一致**：

| 触发原因 | HTTP 状态码 | Header | Body 字段 |
|---|---|---|---|
| Lease 冲突 | **409 Conflict** | `Retry-After: 1` | `retry_after_seconds: 1` |
| 背压超载 | **503 Service Unavailable** | `Retry-After: 1` | `retry_after_seconds: 1` |

> **客户端只需要识别一种"等 X 秒再试"语义**，不用分别处理 409 / 503。这是一种"对客户端 API 友好"的设计。

## 七、Owner 边界保护（最容易被遗漏的纪律）

### 7.1 什么必须阻断 vs 什么可以降级

这是分布式系统最核心的判断：

| 场景 | 行为 | 理由 |
|---|---|---|
| **Lease acquire 失败** | ❌ 阻断（翻 ErrSessionLeaseConflict）| 关系到多实例所有权，继续推进会导致两实例同时改一个 session |
| **Lease renew 失败** | ❌ 阻断（先尝试 acquire，仍失败就翻）| 同上 |
| **Lease release 失败** | ⚠️ 记 log，不影响响应 | release 失败最多让 lease 等 TTL 自然过期，不破坏正确性 |
| **Snapshot save 失败** | ✅ 降级（记 `DegradedReasons["redis_snapshot"]`）| 本地 store 仍有 session，单实例场景不影响；多实例场景这个 session 不能 takeover，但会在报告里提示用户复测 |
| **Snapshot load 失败** | ❌ 阻断 | 跨实例 takeover 必须依赖 snapshot，loadfail = 无法继续 |
| **Event publish 失败** | ✅ 降级（计数 + log，不影响主流程）| SSE 订阅者可能丢事件，但主流程能继续；订阅者会通过 `Last-Event-ID` 重连补齐 |

### 7.2 工程上的纪律

> **"哪些是数据正确性边界 / 哪些是体验降级"，永远要先想清楚再写代码。**
>
> 如果不写明，下次接手的人会随手把 `if err != nil { log.Println(err) }` 加上去，多实例场景就出 bug。

我把这条规则写进了 `CLAUDE.md`：

```
不要做：
- 不要在节点里静默吞掉 LLM 错误；失败必须显式降级并写 `WorkingMemory.DegradedReasons`。
```

## 九、可能的追问与回答

### Q：为什么 lease TTL 选 30 秒？

**A**：
- 太短（如 5 秒）：每次 answer 都要 renew，Redis 压力大；GC 暂停时容易过期
- 太长（如 5 分钟）：实例宕机后接管延迟太大，用户体验差
- 30 秒是 trade-off：覆盖典型用户思考时间（10-30 秒），又能在实例宕机后 30 秒内 takeover

### Q：如果 Redis 也挂了怎么办？

**A**：分两种情况：

1. **临时网络分区**：lease 操作会失败（network error），主流程阻断，客户端等下次连通后继续。这是**正确性优先**的取舍。

2. **Redis 长时间不可用**：可以通过配置不传 `INTERVIEW_REDIS_URL` 退化到单实例模式，只用本地 store + PG。这是 **graceful degradation** 的极端版本。

理想方案是 Redis Sentinel / Cluster 做 HA，但这超出了项目当前 SLA 需求。

### Q：如果客户端不识别 Retry-After 怎么办？

**A**：那就只能等用户手动刷新页面。这是 **协议层契约** 的事，不是后端能完全控制的。前端会在 axios interceptor 里统一处理 409/503 + Retry-After 做自动重试。

### Q：Lua 脚本性能怎么样？

**A**：Redis Lua 脚本在 server 端执行，**没有 round-trip 开销**。renew/release 都是几十微秒级，单实例 Redis 能轻松扛 10万+ QPS 的 Lua eval。瓶颈不在这里。

### Q：能讲一下 jitter 为什么选 `[d/2, d)` 而不是 `[0, d)`？

**A**：
- `[0, d)`（AWS Full Jitter）：完全打散，但可能让某些请求"没等"，对快速重叠的瞬时冲突不利
- `[d/2, d)`（半量抖动）：至少等 d/2，保证 backoff 起作用，同时有 50% 的抖动空间避免雪崩
- 这是经验取舍，没绝对答案。**关键是有 jitter，无 jitter 会出现"所有实例同步重试"的雪崩**

### Q：你用了 Redis 单实例，如果数据丢了怎么办？

**A**：项目 SLA 不要求"绝不丢 session"。即使 Redis 重启丢了所有 lease + snapshot：
- 已经 OC 的面试不受影响（PG 里有完整数据）
- 进行中的面试丢了，用户重新开始一次
- 损失的是 **at-most 几分钟的进度**，不是数据损坏

如果要"绝不丢"，会切到 Redis Sentinel + AOF + everysec fsync，但 IO 开销会上升。**这是 SLA vs 成本的取舍**。
