# 亮点 7：领域模型演进（弱类型 Notes → 强类型协议 + Migration）

> 代码位置：`internal/domain/agent.go`、`internal/domain/migration.go`、`docs/agent-design.md`
> 关键能力：从早期 `Notes map[string]string` 弱类型协议演进到强类型字段，不破坏向后兼容
> 面试官追问命中率：★★★★（DDD / 演进式架构能力的硬证据）

---

## TL;DR（30 秒讲清楚版）

> 项目的领域模型经历了 **3 次重大演进**：
>
> 1. **Stage 1**：节点间用 `Notes map[string]string` 传协议字段（如 `Notes["scored_rounds"] = "5"`），快速搭出主流程
> 2. **Stage 2**：随着字段增多，typo 难以排查、读写要 strconv，**改造成强类型字段**：`ScoredRounds int` / `DegradedRounds int` / `ReflectTopic string` / `DegradedReasons map[string]string`
> 3. **Stage 3**：Stage 6 加多实例后，老 session 已经写到 Redis snapshot / PG state_json，**实现 `MigrateLegacyState` 让新版本读老快照透明转换**
>
> 核心设计：聚合根 `Session` 内嵌 `WorkingMemory`（Agent 状态）、`Rounds[]`（轮次记录）、`Report`（最终汇总）；节点 = 纯函数 + 共享聚合根；Migration 在 Invoke / Resume / LoadSnapshot 入口自动调用，**新旧版本部署可以平滑共存**。

## 一、为什么要演进（不是一开始就强类型）

### 1.1 Stage 1：弱类型 Notes 的价值

**项目早期**：节点之间需要传一些状态字段（已评估轮次数、是否需要补漏），但**还不知道最终需要哪些字段**。

```go
// Stage 1: 协议字段都塞进 Notes
type WorkingMemory struct {
    Notes map[string]string   // 自由扩展的协议字段
}

// 节点写
sess.WorkingMemory.Notes["scored_rounds"] = "5"
sess.WorkingMemory.Notes["reflect_topic"] = "并发"
sess.WorkingMemory.Notes["eval_degraded"] = "true"

// 节点读
n, _ := strconv.Atoi(sess.WorkingMemory.Notes["scored_rounds"])
```

**为什么早期这样设计是对的**：

- **快速迭代**：加新字段不用改 struct 定义，能快速试错
- **协议灵活**：节点作者按需放字段，不影响其他节点
- **DDD 演进式建模**：DDD 推崇"先让模型工作起来，再用 ubiquitous language 提炼"

### 1.2 Stage 1 的痛点（驱动演进）

随着节点数从 3 个加到 9 个，痛点暴露：

| 痛点 | 例子 |
|---|---|
| **typo 不会编译报错** | `scored_round` vs `scored_rounds`，调试半小时 |
| **类型转换噪音** | 每次读都 `strconv.Atoi` / `strconv.ParseBool` |
| **测试难写** | `assert.Equal(t, "5", sess.WorkingMemory.Notes["scored_rounds"])` 不直观 |
| **协议没有"中央定义"** | 想知道有哪些字段要 grep 全代码 |
| **JSON 输出太冗** | `{"notes": {"scored_rounds": "5", ...}}` 比 `{"scored_rounds": 5}` 长 |

### 1.3 Stage 2：强类型重构

**基于"已经知道需要哪些字段"**，把高频协议字段提升为强类型：

```go
// Stage 2 之后：核心协议字段强类型
type WorkingMemory struct {
    // ━━━ 强类型计数器 ━━━
    ScoredRounds   int    // 已评估的轮次数
    DegradedRounds int    // 降级评估的轮次数
    ProbeBudget    int    // 当前剩余的追问预算
    ReflectBudget  int    // 当前剩余的补漏预算

    // ━━━ 强类型标记 ━━━
    ReflectTopic   string // reflection_check 决定的下一题主题（空 = 无补漏需求）

    // ━━━ 强类型降级表 ━━━
    DegradedReasons map[string]string // component → reason

    // ━━━ 高维度数据保留 ━━━
    SkillCoverage   map[string]int      // 技能 → 累计覆盖度
    TopicHistory    []string            // 题目 topic 历史

    // ━━━ 仅留旧状态兼容（不再放主流程协议）━━━
    Notes map[string]string // legacy，会被 MigrateLegacyState 清理
}
```

**重构带来的价值**：

```go
// 编译期类型检查
sess.WorkingMemory.ScoredRounds = 5         // ✅ 不会 typo
sess.WorkingMemory.ScoredRound = 5          // ❌ 编译报错

// 测试更直观
require.Equal(t, 5, sess.WorkingMemory.ScoredRounds)

// JSON 输出更清晰
{"scored_rounds": 5, "degraded_rounds": 1, ...}
```

## 二、聚合根设计（Session）

### 2.1 完整结构

```go
// Session 是面试的聚合根（DDD 术语）
//
// 包含：
//   - 静态输入：JD、简历
//   - 派生分析：JobProfile、ResumeProfile、GapReport
//   - 动态状态：CandidatePool（题库候选）、Rounds[]（每轮回答）、WorkingMemory（Agent 工作记忆）
//   - 终态产物：Report
//   - 流程控制：CurrentNode（暂停/恢复断点）、Status（进行中/完成/失败）
type Session struct {
    // ━━━ Identity ━━━
    ID        string `json:"id"`
    UserID    string `json:"user_id,omitempty"`
    Mode      string `json:"mode"`            // "interactive" | "auto"
    Status    string `json:"status"`          // "active" | "completed" | "failed"
    CreatedAt time.Time `json:"created_at"`
    UpdatedAt time.Time `json:"updated_at"`

    // ━━━ 输入 ━━━
    JDText     string `json:"jd_text,omitempty"`
    ResumeText string `json:"resume_text,omitempty"`

    // ━━━ Setup 阶段产物 ━━━
    JobProfile    *JobProfile    `json:"job_profile,omitempty"`
    ResumeProfile *ResumeProfile `json:"resume_profile,omitempty"`
    GapReport     *GapReport     `json:"gap_report,omitempty"`
    CandidatePool []Question     `json:"candidate_pool,omitempty"`

    // ━━━ Agent loop 状态 ━━━
    Rounds        []*AnswerRound `json:"rounds,omitempty"`
    WorkingMemory *WorkingMemory `json:"working_memory,omitempty"`

    // ━━━ 终态 ━━━
    Report *Report `json:"report,omitempty"`

    // ━━━ Graph 流程控制 ━━━
    CurrentNode string `json:"current_node,omitempty"` // suspend 时保存当前节点
}
```

### 2.2 为什么是 Session 聚合根（不是分散表）

**对比方案**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 分散表（sessions / rounds / reports / working_memory）| 范式化、易索引 | **跨表 join 复杂、事务边界难保证** |
| ✅ **Session 聚合根**（state_json 一张表）| **事务边界清晰**、整体序列化 / 反序列化 | 单 row 偏大 |

**业务特点决定选择**：

- 一次 answer 请求会**同时改 Rounds + WorkingMemory + Report**，作为聚合根写一次最简单
- 题库 query 是低频，可以单独建 question_bank 表
- DDD 推崇"事务边界 = 聚合根边界"

### 2.3 Rounds 的双层结构

```go
type AnswerRound struct {
    RoundID    string                    // UUID
    Number     int                       // 第几轮
    Question   Question                  // 主题
    Answer     string                    // 用户主答案
    Evaluation *Evaluation               // LLM 评估
    Refined    *Evaluation               // refine 节点二次评估（可选）
    Critic     *CriticReport             // critic 节点判信号（可选）
    FollowUps  []*FollowUp               // 追问（嵌套）
    Completed  bool
}

type FollowUp struct {
    Question   string
    Answer     string                    // 用户对追问的答
    Evaluation *Evaluation               // probe_eval 评分
}
```

**为什么 FollowUp 不复用 AnswerRound**：

- 追问只是补充评估，**不是独立轮次**（不算 ScoredRounds）
- 字段子集（没有 Refined / Critic）
- 嵌套结构让"主题 + 追问"在视图层一起渲染

## 三、强类型迁移（Migration）

### 3.1 为什么需要 Migration

**部署中的真实场景**：

```
T0: 部署 v1.0（Stage 1，使用 Notes 弱类型）
T1: 用户开始一些面试，session 写到 PG / Redis snapshot
T2: 部署 v1.1（Stage 2，强类型重构）
T3: 旧 session 还在进行中，被 Redis snapshot LoadSnapshot 加载到新版本
    → 如果不 migrate，sess.WorkingMemory.ScoredRounds 永远是 0
    → 业务逻辑判断"是否到 ReflectBudget"会出错
```

**核心需求**：**新版本读老 snapshot 必须透明转换为新结构**。

### 3.2 MigrateLegacyState 实现

```go
// internal/domain/migration.go
//
// MigrateLegacyState 把旧版本写在 Notes map 里的协议字段提升为强类型字段。
// 设计原则：
//   1. 幂等：调用多次结果一致
//   2. 单向：只把 Notes → 强字段，不会反向写
//   3. 清理：转换后 delete(Notes, key) 让 Notes 只保留真正的非协议字段
//   4. 防御：所有 nil / 类型错都安全跳过，不会 panic
func (s *Session) MigrateLegacyState() {
    if s == nil || s.WorkingMemory == nil {
        return
    }
    wm := s.WorkingMemory

    // ━━ 数值字段：scored_rounds / degraded_rounds / probe_budget 等 ━━
    if wm.ScoredRounds == 0 && wm.Notes != nil {
        if v, ok := wm.Notes["scored_rounds"]; ok {
            if n, err := strconv.Atoi(v); err == nil {
                wm.ScoredRounds = n
            }
            delete(wm.Notes, "scored_rounds")
        }
    }
    if wm.DegradedRounds == 0 && wm.Notes != nil {
        if v, ok := wm.Notes["degraded_rounds"]; ok {
            if n, err := strconv.Atoi(v); err == nil {
                wm.DegradedRounds = n
            }
            delete(wm.Notes, "degraded_rounds")
        }
    }
    // ... ProbeBudget / ReflectBudget 类似 ...

    // ━━ 字符串字段：reflect_topic ━━
    if wm.ReflectTopic == "" && wm.Notes != nil {
        if v, ok := wm.Notes["reflect_topic"]; ok {
            wm.ReflectTopic = v
            delete(wm.Notes, "reflect_topic")
        }
    }

    // ━━ 降级原因表：notes 里所有 *_degraded 后缀的 key 提升到 DegradedReasons ━━
    if wm.Notes != nil {
        for key, value := range wm.Notes {
            if !strings.HasSuffix(key, "_degraded") {
                continue
            }
            component := strings.TrimSuffix(key, "_degraded")
            if wm.DegradedReasons == nil {
                wm.DegradedReasons = map[string]string{}
            }
            if _, exists := wm.DegradedReasons[component]; !exists {
                wm.DegradedReasons[component] = value
            }
            delete(wm.Notes, key)
        }
    }
}
```

### 3.3 关键设计原则

#### ① 幂等（idempotent）

```go
// 调用多次结果一致：
sess.MigrateLegacyState()
sess.MigrateLegacyState()
sess.MigrateLegacyState()
// 第 2、3 次调用：Notes 已经被清理，强字段已经有值，所有 if 分支都跳过
```

**为什么必须幂等**：

- Invoke / Resume / LoadSnapshot 三个入口都会调
- 一次请求可能经历"LoadSnapshot → migrate → Invoke → migrate"两次 migrate
- 不幂等的 migration 会导致计数器双倍 / 字段被覆盖

#### ② 单向（不反写）

```go
// ✅ 只做：Notes["scored_rounds"] → ScoredRounds，删除老 key
// ❌ 不做：ScoredRounds → Notes["scored_rounds"]
```

**为什么单向**：

- Notes 是被淘汰的，不应该让新代码再写
- 如果反写，老版本读新 snapshot 会"看似兼容"，反而**掩盖了升级问题**

#### ③ 清理（delete 老 key）

```go
delete(wm.Notes, "scored_rounds")  // 转换后立即删除
```

**为什么必须删**：

- 不删的话每次 migrate 都会重新走一次条件判断，**浪费 CPU**
- snapshot 序列化时老 key 会一直存在，**让 JSON 越来越大**
- 强字段是 source of truth，老 key 留着会**造成双 source 困惑**

#### ④ 防御（不 panic）

```go
if wm == nil { return }
if v, ok := wm.Notes["scored_rounds"]; ok {
    if n, err := strconv.Atoi(v); err == nil {
        wm.ScoredRounds = n
    }
    // 转换失败也 delete，避免 garbage 留在 Notes
    delete(wm.Notes, "scored_rounds")
}
```

**为什么所有错都跳过**：

- Migration 不应该让"读老 snapshot"失败
- 数据格式异常（如 `Notes["scored_rounds"] = "abc"`）应该容忍，**不要 panic 或 error**
- 异常数据在新强字段上是 0，**比阻断主流程好得多**

### 3.4 Graph 入口自动调用

```go
// internal/graph/graph.go
func (r *Runnable) Invoke(ctx context.Context, sess *domain.Session) error {
    sess.MigrateLegacyState()  // ★ 自动迁移
    return r.run(ctx, sess, []string{r.g.entry})
}

func (r *Runnable) Resume(ctx context.Context, sess *domain.Session) error {
    sess.MigrateLegacyState()  // ★ 自动迁移
    if sess.CurrentNode == "" {
        return fmt.Errorf("...")
    }
    // ...
}
```

```go
// internal/httpapi/redis_session_coordinator.go
func (c *RedisSessionCoordinator) LoadSnapshot(ctx, sessionID) (*Session, error) {
    // ... 反序列化 JSON ...
    sess.MigrateLegacyState()  // ★ 自动迁移
    return &sess, nil
}
```

**为什么放在入口**：

- **节点作者无感知**：新节点只用强字段，不需要懂老协议
- **避免遗漏**：不可能漏调（所有进入图的路径都会过这两个函数）
- **关注点分离**：Migration 是基础设施关心的事，业务逻辑不该耦合

## 四、为什么不一开始就强类型（DDD 演进式建模）

这是个值得讲的反思——**当时为什么没直接强类型**。

### 4.1 不直接强类型的理由

> 早期不知道**最终需要哪些字段**，过早强类型会导致：
>
> - **架构僵化**：每加一个字段要改 struct + 改 schema + 改测试
> - **过度设计**：可能定义了一堆字段但实际用不到
> - **沟通成本高**：需要团队对齐"协议字段长什么样"

### 4.2 演进式建模的指导原则

**Eric Evans DDD 经典 quote**：

> "**Make it work, make it right, make it fast.**"
>
> 第一步只追求 work（弱类型快速搭起来），第二步追求 right（强类型 + Migration），第三步才是 fast（性能优化）。

我的演进路径完全符合这个：

| Stage | 重点 | 标志 |
|---|---|---|
| 1 | Make it work | Notes map 全屏，主流程能跑 |
| 2 | Make it right | 强类型重构 + Migration |
| 3 | Make it fast | （未来）字段索引、JSON Schema 校验、protobuf 序列化 |

### 4.3 哪些字段保留弱类型

```go
type WorkingMemory struct {
    // 强类型核心协议字段
    ScoredRounds int
    // ...

    // 弱类型保留：低频、自由扩展、不影响主流程
    Notes map[string]string
}
```

**判断标准**：

| 字段 | 强 or 弱 | 理由 |
|---|---|---|
| `ScoredRounds` | 强 | 多个节点读写，主流程依赖 |
| `DegradedReasons` | 强（map[string]string）| 多个节点写、报告读，需要稳定 schema |
| `SkillCoverage` | 强（map[string]int）| 高频读写，类型转换烦 |
| `Notes["debug_*"]` | 弱（保留在 Notes）| 调试用、低频、无 schema 必要 |

> **不是所有字段都要强类型**，**主流程协议字段强类型 + 边缘字段弱类型**是最佳实践。

## 五、其他领域模型设计点

### 5.1 Profile 系列（结构化解析结果）

```go
type JobProfile struct {
    Title           string   // "Go 后端工程师"
    YearsExperience int      // 3
    RequiredSkills  []string // ["Go", "Redis", "PostgreSQL"]
    NicetoHave      []string // ["k8s", "gRPC"]
    Responsibilities []string // ["设计微服务", "代码审查"]
}

type ResumeProfile struct {
    Name            string
    YearsExperience int
    Skills          []SkillExperience  // 技能 + 项目时长
    Projects        []Project
    Education       []Education
}

type GapReport struct {
    MatchedSkills   []string
    MissingSkills   []string
    StrengthAreas   []string
    WeakAreas       []string
    OverallMatch    int      // 0-100
}
```

**关键设计**：

- **结构化字段优先于自由文本**：LLM 输出是 JSON schema 强制的（见亮点 3 CallWithSchema）
- **派生数据存聚合根**：JobProfile 是 ParseJD 节点的输出，存到 sess 让下游节点直接读
- **不存原始 prompt / response**：太大，且能从 RecordingChatModel 的 record 重建

### 5.2 Question / Evaluation / CriticReport

```go
type Question struct {
    ID             string
    Content        string
    Tags           []string
    Difficulty     int      // 1-5
    SkillCategory  string
    ExpectedPoints []string  // 期望覆盖的要点（用于 LLM 评估）
}

type Evaluation struct {
    Score          int      // 0-100
    HitPoints      []string // 命中的 ExpectedPoints
    MissedPoints   []string // 漏掉的
    Suggestion     string   // 提升建议
    ExpectedPoints []string // 冗余存储，便于报告独立渲染
}

type CriticReport struct {
    NeedsRefine     bool
    HasProbeSignal  bool
    ProbeTopics     []string  // 建议的追问方向
    ConfidenceScore float64   // critic 自身置信度
}
```

**为什么 Evaluation 冗余存 ExpectedPoints**：

- Question 在 sess.Rounds[].Question 里
- Evaluation 在 sess.Rounds[].Evaluation 里
- 报告页要展示"hit / missed / expected"对比，**冗余存让报告渲染不需要 join**
- 这是**为读优化的反范式化**

## 六、可能的追问与回答

### Q：为什么不用 protobuf 定义 schema？

**A**：
- protobuf 适合**跨服务 RPC**，本项目内部数据流不跨服务
- protobuf 的 codegen 让 IDE 体验变差（一堆 `.pb.go` 文件）
- 当前 `domain` 包就是单一 source of truth，**没有 schema drift 问题**
- 未来有需求暴露给其他系统（如前端 OpenAPI），会考虑切 protobuf 或 JSON Schema

### Q：Migration 万一漏写一个字段会怎样？

**A**：
- 老字段留在 Notes 里，新字段保持 0/空字符串
- 业务逻辑会按"新 session"行为继续，**不会崩**
- 但行为可能不正确（比如 ScoredRounds 一直是 0 → 永远不进入 reflection_check）
- 解决：**完整测试覆盖** + **先在 staging 灰度**

### Q：Session 越来越大怎么办？

**A**：当前一个 session 大约 10-50 KB（10 轮 evaluation + report），可控。
- 未来 1000 轮的极端情况：Rounds 拆到独立表，按 round_id 分页加载
- 当前不优化：**预算冗余足够**，过早优化是恶之源

### Q：CandidatePool 存到 session 里会不会重复存？

**A**：是的，每个 session 都会存一份候选池（10-20 题）。
- 选项 1：存 question_id 列表，每次读都 join 题库（节省空间，多一次查询）
- 选项 2：✅ 完整存（当前选择，事务边界清晰，额外 ~5KB 可接受）

### Q：DegradedReasons 字段会不会膨胀？

**A**：每个 component 只保留**最后一次 reason**（见亮点 4），map 大小上界 ~10 个 entry，可忽略。

### Q：你这套领域模型支持插入新节点吗？

**A**：完美支持。新节点只需要：

1. 实现 `NodeFunc(ctx, *Session) error`
2. 在 `BuildInterviewGraph` 里 `AddNode + AddEdge / AddBranch`
3. 如果需要新协议字段：先放 Notes（实验阶段），稳定后再提升强类型 + 写 Migration

**这是开闭原则的体现**：新节点不用改 Session 结构。
