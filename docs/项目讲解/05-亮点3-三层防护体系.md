# 亮点 3：三层防护体系（HTTP 背压 + 熔断 + 进程内并发限流）

> 代码位置：`internal/httpapi/middleware_inflight.go`（背压）、`internal/llm/breaker.go`（熔断）、`internal/llm/limited.go`（限流）
> 关键能力：保护慢且不稳定的外部 LLM 依赖，避免雪崩
> 面试官追问命中率：★★★★★（金山云稳定性岗位最关心）

---

## TL;DR（30 秒讲清楚版）

> 调外部 LLM 是慢（3-5 秒）、不稳定（限流/抖动/超时）、按量计费的依赖，必须做三层防护：
>
> ```
> HTTP Request
>     ↓
> [1] MaxInFlightMiddleware  (HTTP 入口背压，超限 503 + Retry-After，非阻塞 try-acquire)
>     ↓
> InterviewService
>     ↓
> [2] BreakingChatModel      (熔断器：closed → open → halfOpen，open 时 ErrBreakerOpen)
>     ↓
> [3] LimitedChatModel       (进程内并发 limiter，等闸门时尊重 ctx)
>     ↓
> RealChatModel (调外部 LLM)
> ```
>
> 三层各管不同的失败模式：**背压防止请求堆积**、**熔断防止依赖雪崩**、**限流防止资源耗尽**。三个不能合并、不能少、顺序不能乱。

---

## 一、为什么需要三层

### 1.1 单层防护的盲点

| 只做 1 层 | 解决的问题 | 留下的问题 |
|---|---|---|
| 只做限流 | 不会一次打死 LLM | LLM 自己挂了，请求会一直堆积消耗自家资源 |
| 只做熔断 | LLM 挂时立刻 fail-fast | 正常时大量并发能打死 LLM；客户端请求堆在服务端 |
| 只做背压 | 服务端不堆积 | LLM 慢时会消耗所有 slot；LLM 挂时还会一直试 |

### 1.2 三层各自的职责

```
┌──────────────────────────────────────────────────────────────┐
│ [1] HTTP 入口背压（MaxInFlightMiddleware）                     │
│  目的：防止"客户端连接堆在服务端"，超载立刻 503                  │
│  作用域：/api/interview/start, /api/interview/answer            │
│  不作用：/healthz, /readyz, /sessions, /stream                  │
│  实现：buffered chan 非阻塞 try-acquire                        │
└──────────────────────────────────────────────────────────────┘
                            │
                            ↓
┌──────────────────────────────────────────────────────────────┐
│ [2] 熔断器（BreakingChatModel）                                │
│  目的：LLM 挂时立刻 fail-fast，不消耗 limiter 槽位              │
│  状态：closed → open → halfOpen → closed                       │
│  阈值：连续 5 次 ErrTransient/DeadlineExceeded 触发 open        │
│  open 时长：30 秒                                              │
│  open 时返回：ErrBreakerOpen（新哨兵，不是 ErrTransient）       │
└──────────────────────────────────────────────────────────────┘
                            │
                            ↓
┌──────────────────────────────────────────────────────────────┐
│ [3] 进程内并发 Limiter（LimitedChatModel）                     │
│  目的：保护真正的稀缺资源（LLM 配额 + 钱）                      │
│  默认：max_concurrency = 4                                     │
│  实现：buffered chan 阻塞 acquire（等闸门时尊重 ctx）           │
└──────────────────────────────────────────────────────────────┘
                            │
                            ↓
                       RealChatModel
```

## 二、为什么是这个顺序（最容易被追问）

### 2.1 顺序不能乱

**错误顺序 1：Limiter 在最外**
```
HTTP → Limiter → Breaker → Real
```
问题：Limiter 不知道下游是否健康。LLM 挂了之后，**所有请求都会先抢 limiter 槽位再被 Breaker 挡回**，相当于 limiter 变成"无效阻塞器"。

**错误顺序 2：Breaker 在最内**
```
HTTP → Limiter → Real（内部有 Breaker）
```
问题：Breaker 应该独立于 Real 实现，否则换 LLM provider 时要重写。

**正确顺序：Breaker 在 Limiter 外**
```
HTTP → Breaker → Limiter → Real
```
理由：
- Breaker open 时直接返回 `ErrBreakerOpen`，**零成本短路**，不消耗 Limiter 槽位
- Limiter 紧挨 Real，保护真正稀缺的下游资源

### 2.2 决定顺序的判断公式

> **"越快能 fail-fast 的应该越外层"**
>
> - 背压："队列满了"判断只要看 chan 长度，O(1)
> - 熔断：判断当前状态 + 时间，O(1)
> - 限流：可能要 sleep 等闸门，O(N)
> - 真实 LLM：网络往返 3-5 秒

按这个公式排序：HTTP 背压 → 熔断 → 限流 → 真实调用。

## 三、Layer 1：HTTP 入口背压（最外）

### 3.1 完整代码

```go
const inflightRetryAfter = time.Second

// MaxInFlightMiddleware 是最外层入口背压：
// 用 buffered chan 当信号量，超过 limit 时非阻塞直接 503，不排队。
func MaxInFlightMiddleware(limit int) gin.HandlerFunc {
    if limit <= 0 {
        return func(c *gin.Context) { c.Next() }   // 关闭背压
    }
    sem := make(chan struct{}, limit)
    return func(c *gin.Context) {
        select {
        case sem <- struct{}{}:        // 非阻塞 try-acquire
            defer func() { <-sem }()
            c.Next()
        default:                       // 立刻拒绝
            retryAfterSeconds := int(inflightRetryAfter.Seconds())
            c.Header("Retry-After", strconv.Itoa(retryAfterSeconds))
            c.AbortWithStatusJSON(http.StatusServiceUnavailable, gin.H{
                "error":               "server busy",
                "retry_after_seconds": retryAfterSeconds,
            })
        }
    }
}
```

### 3.2 设计要点（每一点都能讲）

| 设计 | 选择 | 理由 |
|---|---|---|
| **信号量** | buffered chan | Go idiom，比 `golang.org/x/sync/semaphore` 简单 |
| **acquire 模式** | **非阻塞** try-acquire (`select default`) | 排队等于把客户端连接挂在服务端，浪费资源 |
| **超载响应** | 503 + Retry-After | 标准 HTTP 语义，客户端框架/浏览器都能识别 |
| **协议复用** | 与 Lease 冲突的 409 用同一个 `retry_after_seconds` 字段 | 客户端只识别一种"等 X 秒"语义 |
| **limit <= 0 退化** | no-op middleware | dev / 测试不被打扰；生产环境靠 config.Validate 强校验 |
| **错误格式** | 直接 `c.AbortWithStatusJSON`，不经过业务错误处理 | 业务代码无感知 |

### 3.3 关键设计：为什么不全局挂

```go
// router.go 节选
func registerInterviewRoutes(r *gin.RouterGroup, srv *Server, maxInFlight int) {
    api := r.Group("/interview")

    // 只对 start / answer 挂背压
    api.POST("/start",  MaxInFlightMiddleware(maxInFlight), srv.startInterview)
    api.POST("/answer", MaxInFlightMiddleware(maxInFlight), srv.answerInterview)

    // 健康检查、SSE 流、读路径不挂
    r.GET("/healthz",            srv.healthz)
    r.GET("/readyz",             srv.readyz)
    api.GET("/sessions",         srv.listInterviewSessions)
    api.GET("/sessions/:id",     srv.getInterviewSession)
    api.GET("/interview/stream", srv.streamInterview)   // 长连接独立处理
}
```

**三类路由的不同特点**：

| 路由 | 类型 | 背压策略 | 理由 |
|---|---|---|---|
| `/healthz` `/readyz` | k8s 探针 | ❌ 不背压 | 拦截会被误判挂掉重启 |
| `/sessions`（读） | 短请求、不调 LLM | ❌ 不背压 | 不消耗 LLM 资源，没必要拒绝 |
| `/stream` | SSE 长连接（分钟级）| ⚠️ **独立计数器**（TODO）| 用同一个 chan 会被长连接占满 |
| `/start` `/answer` | 短请求、调 LLM | ✅ **背压** | 真正消耗资源的路径 |

## 四、Layer 2：熔断器（中间）

### 4.1 状态机

```
   ┌─────────┐  连续 N 次失败  ┌────────┐
   │ closed  │ ─────────────> │  open  │
   │ (正常)  │                 │(fail-fast)│
   └─────────┘                 └────────┘
        ▲                           │
        │ probe 成功                │ openDuration 过去
        │                           ▼
   ┌──────────┐  probe 失败    ┌──────────┐
   │ closed   │ <──回去重置  ──│ halfOpen │
   │ (重置)   │                │ (探测)   │
   └──────────┘                └──────────┘
```

### 4.2 完整代码

```go
type BreakingChatModel struct {
    inner        ChatModel
    threshold    int
    openDuration time.Duration
    now          func() time.Time  // 可注入，测试用虚拟时钟

    mu                  sync.Mutex
    state               breakerState
    consecutiveFailures int
    openedAt            time.Time
    halfOpenInFlight    bool       // 关键：保证 halfOpen 同时只有 1 个 probe
}

func (m *BreakingChatModel) Generate(ctx context.Context, messages []Message, opts Options) (*Response, error) {
    allowed, isProbe := m.tryAcquire(ctx)
    if !allowed {
        return nil, ErrBreakerOpen   // 新哨兵，不是 ErrTransient
    }
    resp, err := m.inner.Generate(ctx, messages, opts)
    m.recordResult(ctx, err, isProbe)
    return resp, err
}
```

### 4.3 tryAcquire：决定是否放行

```go
func (m *BreakingChatModel) tryAcquire(ctx context.Context) (bool, bool) {
    m.mu.Lock()
    defer m.mu.Unlock()

    switch m.state {
    case breakerClosed:
        return true, false   // 永远允许，非 probe

    case breakerOpen:
        if m.now().Sub(m.openedAt) < m.openDuration {
            return false, false   // 还在熔断期，拒绝
        }
        // open → halfOpen，发出第一个 probe
        m.transitionLocked(ctx, breakerHalfOpen, "open_duration_elapsed")
        m.halfOpenInFlight = true
        return true, true

    case breakerHalfOpen:
        if m.halfOpenInFlight {
            return false, false   // 已有 probe 在飞，拒绝其他并发
        }
        m.halfOpenInFlight = true
        return true, true
    }
    return false, false
}
```

### 4.4 recordResult：根据失败类型决定是否计数

```go
// shouldCount 决定一个错误是否算"provider 在抽风"
func (m *BreakingChatModel) shouldCount(err error) bool {
    if err == nil {
        return false
    }
    if errors.Is(err, ErrBreakerOpen)    { return false }  // 自身 fail-fast 不算（防自激）
    if errors.Is(err, context.Canceled)  { return false }  // 客户端主动取消不算
    if errors.Is(err, ErrPermanent)      { return false }  // 永久配置错不算
    if errors.Is(err, ErrSchemaInvalid)  { return false }  // 模型输出 schema 错不算
    if errors.Is(err, ErrTransient)              { return true }  // 计入：传输层瞬时错
    if errors.Is(err, context.DeadlineExceeded)  { return true }  // 计入：请求超时
    return false   // 未分类错误：保守地不计入，避免业务 bug 放大成熔断
}
```

### 4.5 错误分类（最核心的设计点）

**为什么有的错算、有的错不算**：

| 错误 | 计入熔断 | 理由 |
|---|---|---|
| `ErrTransient` | ✅ 计入 | 真实的 provider 瞬时故障（5xx、连接超时、限流） |
| `context.DeadlineExceeded` | ✅ 计入 | 整体请求超时（可能 LLM 慢，也可能网络抖） |
| `context.Canceled` | ❌ 不计入 | **客户端主动断开**。如果计入会出现"用户大量取消请求 → 熔断器误触发 → 真实请求被熔断"的级联故障 |
| `ErrPermanent` | ❌ 不计入 | API key 错、prompt 格式错。重试 100 次也不会好；而且这类错通常很快返回，**会"刷分"让熔断器一直 closed** |
| `ErrSchemaInvalid` | ❌ 不计入 | LLM 返回了不符合 JSON schema 的内容。**这是 prompt 工程问题，不是 LLM 服务可用性问题** |
| `ErrBreakerOpen` | ❌ 不计入 | 自己 fail-fast 的错。**计入会导致 halfOpen 探测时自激** |
| 未分类错误 | ❌ 不计入 | 保守原则：宁可漏熔断不要误熔断 |

**这是和 Hystrix 默认"所有 Exception 都算"最大的区别**——错误分类驱动的熔断更精准。

### 4.6 为什么 open 时返回新哨兵 ErrBreakerOpen

```go
// 关键设计：不能 wrap ErrTransient
var ErrBreakerOpen = errors.New("llm: circuit breaker open")
```

**如果用 `ErrTransient` 包装会怎样**：

1. 上游调用者（节点里的 LLM 调用代码）看到 `ErrTransient`
2. 节点级 Retry 装饰器认为"这是临时故障，应该重试"
3. 重试 3 次都被熔断 → 浪费时间还不解决问题

**用独立哨兵的好处**：

- 上游识别到 `ErrBreakerOpen` → 走**降级 fallback 路径**（规则评分 / 默认题目）
- 不会触发任何重试
- `WorkingMemory.DegradedReasons[component] = "breaker_open"` 显式记录

### 4.7 halfOpen 单 probe 设计

```go
case breakerHalfOpen:
    if m.halfOpenInFlight {
        return false, false   // 已有 probe 在飞，其他并发拒绝
    }
    m.halfOpenInFlight = true
    return true, true
```

**为什么只允许 1 个 probe**：

- halfOpen 期间不知道 provider 是否真恢复
- 如果允许 100 个并发请求同时探测，万一 provider 只恢复一半，会**瞬间把还没完全恢复的下游又打挂**
- 1 个 probe 成功 → 转 closed，所有请求重新放行
- 1 个 probe 失败 → 转回 open，再等 openDuration

这是 Netflix Hystrix 推荐的实践。

### 4.8 readyz 集成（关键工程取舍）

```go
// State() 暴露给 /readyz 用
func (m *BreakingChatModel) State() string {
    m.mu.Lock()
    defer m.mu.Unlock()
    return m.state.String()  // "closed" / "open" / "half_open"
}

// /readyz handler
func (s *Server) readyz(c *gin.Context) {
    state := s.breaker.State()
    if state == "open" {
        // 关键：返回 200 + degraded，而不是 503
        c.JSON(http.StatusOK, gin.H{
            "status":       "degraded",
            "llm_breaker":  "open",
        })
        return
    }
    c.JSON(http.StatusOK, gin.H{"status": "ok"})
}
```

**为什么 readyz 返回 200 degraded 而不是 503**：

> 熔断 open 时**节点降级路径仍可答题**（规则评分），pod 仍然能处理请求。
>
> 如果 readyz 返回 503，k8s 会把 pod 从 Service 拉走，反而损失可用容量。
>
> degraded 状态需要被监控告警，但**流量正常分发**。

类比：Netflix Hystrix dashboard 的思路——熔断打开不代表服务挂了，代表服务正在"保护性降级"。

## 五、Layer 3：进程内并发 Limiter（最内）

### 5.1 完整代码

```go
type LimitedChatModel struct {
    inner ChatModel
    sem   chan struct{}
}

func NewLimitedChatModel(inner ChatModel, maxConcurrent int) ChatModel {
    if inner == nil || maxConcurrent <= 0 {
        return inner   // 无限制时透传
    }
    return &LimitedChatModel{
        inner: inner,
        sem:   make(chan struct{}, maxConcurrent),
    }
}

func (m *LimitedChatModel) Generate(ctx context.Context, messages []Message, opts Options) (*Response, error) {
    if err := m.acquire(ctx); err != nil {
        return nil, err
    }
    defer m.release()
    return m.inner.Generate(ctx, messages, opts)
}

func (m *LimitedChatModel) acquire(ctx context.Context) error {
    if ctx == nil {
        ctx = context.Background()
    }
    select {
    case m.sem <- struct{}{}:
        return nil
    case <-ctx.Done():
        return fmt.Errorf("llm concurrency limit wait: %w", ctx.Err())
    }
}
```

### 5.2 与 HTTP 背压的区别

| 维度 | HTTP 背压（Layer 1）| Limiter（Layer 3）|
|---|---|---|
| **acquire 模式** | 非阻塞 try-acquire | **阻塞 acquire**（等闸门）|
| **超载行为** | 立刻 503 | 等待 + ctx 超时退出 |
| **保护对象** | 服务端连接 | 外部 LLM 配额 + 钱 |
| **场景** | 客户端突发流量 | 内部慢调用累积 |

**为什么 Limiter 用阻塞**：

- HTTP 背压是边界，超过就让客户端走（背压协议）
- Limiter 是内部资源分配，应该让请求**排队等闸门**，而不是直接拒绝
- 但**等的时候必须尊重 ctx**——如果客户端断开或上层 timeout，立刻退出，不再继续 acquire

### 5.3 Stream 路径的特殊处理

```go
func (m *LimitedChatModel) Stream(ctx context.Context, messages []Message, opts Options) (<-chan Chunk, error) {
    if err := m.acquire(ctx); err != nil {
        return nil, err
    }
    ch, err := m.inner.Stream(ctx, messages, opts)
    if err != nil {
        m.release()                   // 启动失败立刻释放
        return nil, err
    }
    out := make(chan Chunk)
    go func() {
        defer m.release()             // 关键：在 goroutine 退出时才释放
        defer close(out)
        for chunk := range ch {
            select {
            case <-ctx.Done():
                out <- Chunk{Err: ctx.Err(), Done: true}
                return
            case out <- chunk:
            }
        }
    }()
    return out, nil
}
```

**坑点**：Stream 调用返回后，**chunk 还在流式产出**，所以 slot 必须等到 chunk 全部消费完才能释放。

## 六、装配链路（cmd/server/main.go）

```go
// internal/llm/factory.go 提供统一构造
func BuildChatModel(cfg config.LLMConfig) (ChatModel, error) {
    // 1. 构造 RealChatModel
    real, err := NewRealChatModel(cfg)
    if err != nil {
        return nil, err
    }

    // 2. 套 Limiter（紧挨着 Real）
    limited := NewLimitedChatModel(real, cfg.MaxConcurrency)

    // 3. 套 Breaker（在 Limiter 外面）
    breaker := NewBreakingChatModel(limited, cfg.BreakerFailureThreshold, cfg.BreakerOpenDuration)

    // 4. 套 Recording（最外，记录所有调用）
    return NewRecordingChatModel(breaker), nil
}
```

**装饰器顺序**：

```
RecordingChatModel → BreakingChatModel → LimitedChatModel → RealChatModel
       ↑                  ↑                    ↑
   记录所有调用        熔断 fail-fast       并发限流
   （含 ErrBreakerOpen）（不消耗 limiter 槽位）（保护 LLM 配额）
```

**为什么 Recording 在最外**：

> 需要记录 `ErrBreakerOpen` 和 `context.Canceled` 这种**被装饰器自己拦截的错误**，所以必须包在最外面，能看到完整结果。

## 七、超时处理（与三层防护正交）

### 7.1 多层超时

```
HTTP 请求 timeout (gin)         → 30 秒
  ↓
LLM 调用 timeout (节点设置)      → 10 秒
  ↓
单次 HTTP roundtrip timeout      → 8 秒
  ↓
TCP dial timeout                 → 3 秒
```

**关键纪律：内层 timeout < 外层 timeout**，否则外层 timeout 永远不会触发。

### 7.2 ctx 传递

```go
// 节点里
func (n *PickNextNode) Run(ctx context.Context, sess *domain.Session) error {
    // 派生子 ctx，10 秒后自动 cancel
    callCtx, cancel := context.WithTimeout(ctx, 10*time.Second)
    defer cancel()

    resp, err := n.chatModel.Generate(callCtx, messages, opts)
    if errors.Is(err, context.DeadlineExceeded) {
        // 走规则 fallback
        markDegraded(sess, "pick", "llm_timeout")
        return n.pickByRule(sess)
    }
    return err
}
```

## 八、可能的追问与回答

### Q：为什么不用 `golang.org/x/sync/semaphore`？

**A**：那个包功能更多（支持 N 个 token），但 buffered chan 已经够用 + 更简单。**SRE 原则：能用标准库就不引第三方**。

### Q：熔断器 threshold = 5 怎么选的？

**A**：经验值，太小（如 2）容易被噪声触发，太大（如 50）发现得太晚。5 次连续失败是"明显 LLM 在抽风"的强信号。生产环境会根据真实 SLA 调整。

### Q：openDuration = 30 秒怎么选的？

**A**：
- 太短（5 秒）：LLM 可能还没恢复就放探测，反复熔断
- 太长（5 分钟）：恢复后用户等太久
- 30 秒是 LLM provider 典型故障的恢复时间（限流 5-10 秒、轻微故障 10-30 秒、严重故障可能要分钟级）

### Q：max_concurrency = 4 怎么选的？

**A**：LLM provider 给的 RPM（每分钟请求数）配额决定。比如配额 60 RPM，按平均 3 秒/请求算 = 20 req/min = 0.33 req/s = 同时最多 ~3 个 in-flight。**4 给一点 buffer，但留余量给突发**。

### Q：三层防护能扛多少 QPS？

**A**：
- 单实例：限制是 `max_concurrency * (1 / 平均延迟)` = `4 / 3s = 1.3 req/s`
- 多实例水平扩展：N 实例就是 N * 1.3 req/s（前提是 LLM provider 配额够）
- **瓶颈永远在 LLM**，三层防护是为了"瓶颈时优雅降级"，不是为了"扛更多 QPS"

### Q：能不能合并 Layer 1 和 Layer 3？

**A**：不行。
- Layer 1 是**全局服务端连接保护**（防客户端突发）
- Layer 3 是**LLM 资源保护**（防 LLM 配额耗尽）
- 不同路由共享 Layer 3（所有调 LLM 的节点），但 Layer 1 只挂在 LLM 路径的 HTTP 入口

### Q：能不能合并 Layer 2 和 Layer 3？

**A**：不行。
- Layer 2（熔断）关心"LLM 是不是挂了"
- Layer 3（限流）关心"我并发是不是太多"
- 这是两个独立的失败模式，要分别处理

### Q：如果 Provider 实际支持 100 并发，你这 4 是不是太保守？

**A**：是的，**这是 personal 项目的取舍**（避免账单爆炸）。生产环境会根据真实压测调高。**关键不是数字，是机制——配置项可以改，但三层防护的架构不能少**。

### Q：背压用 buffered chan 而不是 ring buffer / token bucket，性能能扛吗？

**A**：buffered chan 的 send/recv 是 Go runtime 优化过的，**单核能扛 50万+ QPS**。瓶颈不在背压本身。如果用 token bucket（如 rate.Limiter）反而引入更多锁竞争。

### Q：你这个熔断器没有半开期慢启动，是不是 too simple？

**A**：是的，正式生产可以加 **半开期渐进放行**（每秒放行 N 个，逐步加大）。我现在只放 1 个 probe，简单可靠，**对个人项目 SLA 足够**。Hystrix 标准实现也是单 probe。
