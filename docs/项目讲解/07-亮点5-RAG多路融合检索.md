# 亮点 5：RAG 多路融合检索（pgvector + LinearFusion）

> 代码位置：`internal/retriever/pgvector.go`、`fusion.go`、`internal/nodes/retrieve_rag.go`、`cmd/reindex/`
> 核心能力：HNSW 向量召回 + GIN tag 召回双路并行，Go 端三路加权融合
> 面试官追问命中率：★★★★（RAG 是当下面试热点，但大部分人只会"调向量库"）

---

## TL;DR（30 秒讲清楚版）

> RAG 检索做的不是"调一下向量库"，而是 **两阶段架构**：
>
> 1. **PG 端两路并行召回**：HNSW 索引扫向量候选（`embedding <=> $1::vector`）+ GIN 索引扫 tag 候选（`tags && $2::text[]`），UNION 去重
> 2. **Go 端 LinearFusion 三路加权融合**：vector_score (0.6) + topic_score (0.3) + difficulty_score (0.1)
>
> 关键工程细节：
> - **CTE MATERIALIZED**：强制物化向量候选 CTE，避免 PG 优化器内联导致 HNSW 索引失效
> - **SET LOCAL hnsw.ef_search**：事务级调整 HNSW 召回精度，不污染连接池其他 session
> - **难度软过滤**：`difficulty BETWEEN target-2 AND target+2`，超出范围 SQL 层直接剪枝
> - **稳定排序**：score 相同时按 ID 排，保证可复现（单测友好）
> - **打分权重在 Go 而非 SQL**：A/B 实验调权重无需改 SQL
> - **离线 reindex CLI** 与在线服务解耦，重建 embedding 不影响业务

---

## 一、为什么需要"多路融合"而不是单纯向量检索

### 1.1 单纯向量检索的痛点

```sql
-- 朴素方案
SELECT * FROM question_bank
ORDER BY embedding <=> $1::vector
LIMIT 5;
```

**问题**：

| 场景 | 单纯向量检索的失败模式 |
|---|---|
| JD 是 **Go 后端**，召回了 **Python 后端** 的题 | embedding 空间里 Go 后端和 Python 后端语义太近 |
| 想要 **中等难度**，召回了 **简单题** | 向量空间不感知难度数值字段 |
| 想要 **并发主题**，召回了 **分布式锁**（语义相近但话题跑偏）| 缺少话题约束 |

### 1.2 多路融合的思路

```
单一信号 → 多信号融合
─────────────────
vector_score    (语义相似度，主权重)
topic_score     (tag 命中率，话题约束)
difficulty_score(难度匹配度，tie-breaker)
─────────────────
final_score = 0.6*vector + 0.3*topic + 0.1*difficulty
```

**为什么是这个权重**：

> - **0.6 vector 主导**：实测向量召回最稳，主导排序合理
> - **0.3 topic 防跑题**：tag 0.3 足以让"话题完全跑偏"的题目被压下去
> - **0.1 difficulty 收尾**：是 tie-breaker，不该主导

**权重在 Go 而非 SQL**：A/B 实验调权重不用改 SQL、不用重建索引，**直接热调即可**。

## 二、两阶段架构（核心设计）

```
              ┌────────────────────────────────────┐
              │ Stage 1: PG 端候选召回（两条索引扫描）│
              │                                    │
              │ vector_candidates: HNSW + difficulty 软过滤│
              │ tag_candidates:    GIN  + difficulty 软过滤│
              │           ↓ UNION 去重                  │
              │       原始特征（vec_dist + tag_overlap）│
              └────────────────────────────────────┘
                              ↓
              ┌────────────────────────────────────┐
              │ Stage 2: Go 端 LinearFusion 打分    │
              │                                    │
              │ vs = 1 - cos_distance              │
              │ ts = tag_overlap / query_tag_count │
              │ ds = 1 - |diff - target|/2         │
              │ score = 0.6*vs + 0.3*ts + 0.1*ds   │
              │           ↓ 降序排 + 截取 TopK         │
              │           Results[]                │
              └────────────────────────────────────┘
```

### 2.1 为什么不在 PG 里一把梭

**朴素想法**：写一个大 SQL，把三路融合直接放在 ORDER BY 里。

```sql
-- ❌ 反例
SELECT *
FROM question_bank
ORDER BY 0.6*(1 - embedding <=> $1::vector)
       + 0.3*(...tag_overlap...)
       + 0.1*(1 - abs(difficulty - $3)/2.0) DESC
LIMIT 5;
```

**为什么这是错的**：

1. **HNSW 索引会失效**：HNSW 只在 `ORDER BY embedding <=> ?` 时被利用，加上别的算术表达式后 planner 会走全表扫描
2. **权重调整成本高**：每次 A/B 实验都要改 SQL，PG 优化器还要重新评估 plan
3. **不易解释**：单个 score 无法分解出"是 vector 主导还是 tag 主导"

### 2.2 正确做法：两阶段切分

| 阶段 | 在哪 | 做什么 | 索引利用 |
|---|---|---|---|
| Stage 1 | **PG 端** | 两条独立索引扫描召回候选（数量是最终 K 的 5-8 倍）| ✅ HNSW + GIN 都能用 |
| Stage 2 | **Go 端** | 对小候选集做加权排序 | 内存计算，无索引开销 |

> **核心原则**：PG 只做它擅长的（索引扫描），Go 做它擅长的（业务逻辑 + A/B 配置热调）。

## 三、SQL 设计（每一行都有取舍）

### 3.1 完整 SQL

```sql
WITH vector_candidates AS MATERIALIZED (
    SELECT id, embedding <=> $1::vector AS vec_dist
    FROM question_bank
    WHERE difficulty BETWEEN GREATEST($3 - 2, 1) AND LEAST($3 + 2, 5)
    ORDER BY embedding <=> $1::vector
    LIMIT $4
),
tag_candidates AS MATERIALIZED (
    SELECT id
    FROM question_bank
    WHERE tags && $2::text[]
      AND difficulty BETWEEN GREATEST($3 - 2, 1) AND LEAST($3 + 2, 5)
    LIMIT $5
),
candidates AS (
    SELECT id FROM vector_candidates
    UNION
    SELECT id FROM tag_candidates
)
SELECT
    q.id, q.content, q.tags, q.difficulty, q.skill_category, q.expected_points,
    COALESCE(vc.vec_dist, q.embedding <=> $1::vector) AS vec_dist,
    (SELECT count(*)::int FROM unnest(q.tags) t WHERE t = ANY($2::text[])) AS tag_overlap
FROM candidates c
JOIN question_bank q USING (id)
LEFT JOIN vector_candidates vc USING (id);
```

### 3.2 每个细节的取舍

#### ① CTE MATERIALIZED（最重要的关键字）

```sql
WITH vector_candidates AS MATERIALIZED (...)
```

**没加 MATERIALIZED 会怎样**：

PG 12+ 的优化器会**默认内联 CTE**——把 CTE 主体展开到外层查询里。这看起来是好事（避免临时表），但对 HNSW 是灾难：

- 内联后 PG 看到的是 `SELECT ... FROM q WHERE ... ORDER BY embedding <=> $1::vector LIMIT 5`，但**外层还有 JOIN candidates**，planner 可能选择不走 HNSW
- **MATERIALIZED 强制物化**，让 HNSW 索引扫描在 CTE 内独立完成

#### ② 难度软过滤

```sql
WHERE difficulty BETWEEN GREATEST($3 - 2, 1) AND LEAST($3 + 2, 5)
```

**为什么是 ±2 而不是精确匹配**：

- 目标难度 3 时召回 [1,5]，目标难度 5 时召回 [3,5]
- 太严格会让向量候选池变小，影响最终多样性
- ±2 之外的题：SQL 层直接剪枝（不让进入向量计算的成本中）

**为什么用 `GREATEST(.., 1) AND LEAST(.., 5)`**：

- 难度范围是 1-5，目标 = 1 时下界应该是 1 不是 -1
- 这是兜底，防止参数边界 bug

#### ③ Vector candidate 数 vs Tag candidate 数

```go
// 默认值
vecN := K * 5    // 向量候选取 5 倍
tagN := K * 3    // tag 候选取 3 倍
```

**为什么 vector 取得多**：

- vector 主导排序（权重 0.6），需要更多候选保证 Top-K 质量
- tag 只是约束 + 补充，3 倍够用
- 候选总数上界 K*8 = 40 条（K=5 时），融合阶段的 O(40) 排序成本忽略不计

#### ④ COALESCE 兜底 vec_dist

```sql
COALESCE(vc.vec_dist, q.embedding <=> $1::vector) AS vec_dist
```

**为什么需要**：

- `candidates = vector_candidates UNION tag_candidates`
- 对于 **tag-only 命中**（vector_candidates 里没有但 tag_candidates 里有）的题，`vc.vec_dist` 是 NULL
- COALESCE 兜底**现场算一次余弦距离**，让 fusion 阶段所有候选都有 vec_dist 字段
- 这是 SeqScan over 候选集（至多 K*3 行），开销可忽略

#### ⑤ tag_overlap 计算

```sql
(SELECT count(*)::int FROM unnest(q.tags) t WHERE t = ANY($2::text[])) AS tag_overlap
```

**为什么用 subquery + unnest**：

- 计算 `q.tags ∩ $2` 的元素个数
- 在 PG 16+ 上比 `array_intersection` 风格的扩展函数更稳定
- 子查询每行执行一次，候选集小（~K*8 行），无性能问题

### 3.3 SET LOCAL hnsw.ef_search（精度热调）

```go
// 进入事务后立刻调整 HNSW 召回精度
if _, err := tx.Exec(ctx, "SET LOCAL hnsw.ef_search = "+strconv.Itoa(r.EfSearch)); err != nil {
    // 不致命——SET 失败大概率是 pgvector 版本不支持该参数，
    // 降级走默认 ef_search=40 也能用
    _ = err
}
```

**为什么是 SET LOCAL 而不是 SET / ALTER SYSTEM**：

| 命令 | 生效范围 | 缺点 |
|---|---|---|
| `ALTER SYSTEM SET` | 全局永久 | 改完要重启，影响所有连接 |
| `SET` | 当前 session | **污染连接池**：其他 session 拿到这个连接时会继承设置 |
| ✅ `SET LOCAL` | **当前事务** | 事务结束自动还原，对连接池友好 |

**为什么 ef_search = 100**：

- 默认 40 召回率低（HNSW 走的层数少）
- 100-200 是 pgvector 官方推荐的生产值，召回率 95%+
- 越大越慢，100 是召回率 / 性能的平衡点

## 四、Fusion 打分（Go 端）

### 4.1 接口设计（为未来 swap 留口）

```go
type Fusion interface {
    Fuse(candidates []Candidate) []Result
}

// 当前只有 LinearFusion 一个实现
// 未来可能加：
//   - RRFFusion：Reciprocal Rank Fusion，特征尺度不齐时用
//   - CrossEncoderFusion：调外部 reranker 模型（如 bge-reranker）
```

> **抽接口是为了"未来 swap 实现无需改 retriever 主流程"**——这是依赖倒置的典型应用。

### 4.2 三路打分细节

```go
func (f *LinearFusion) Fuse(candidates []Candidate) []Result {
    results := make([]Result, 0, len(candidates))
    for _, c := range candidates {
        // ① vector_score = 1 - cosine_distance，clamp 到 [0,1]
        vs := 1.0 - c.VecDist
        vs = clamp01(vs)

        // ② tag_score = intersection / query_tag_count
        // query 没传 tag 时（QueryTagCount=0）固定 0 分，不影响纯 vector 检索
        var ts float64
        if c.QueryTagCount > 0 {
            ts = float64(c.TagOverlap) / float64(c.QueryTagCount)
        }
        ts = clamp01(ts)

        // ③ difficulty_score = 1 - |diff - target| / 2
        // 跨度用 2 是因为软过滤就是 ±2，超出范围已经被 SQL filter 掉了
        // 此处分母 2 让 ±1 时得 0.5、±2 时得 0、=target 时得 1
        ds := 1.0 - math.Abs(float64(c.Difficulty-c.TargetDiff))/2.0
        ds = clamp01(ds)

        score := f.WeightVector*vs + f.WeightTopic*ts + f.WeightDifficulty*ds

        results = append(results, Result{
            ID:              c.ID,
            Content:         c.Content,
            Score:           score,
            VectorScore:     vs,
            TagScore:        ts,
            DifficultyScore: ds,
        })
    }

    // 按 score 降序排。Score 相同时按 ID 排，保证稳定可复现（单测友好）
    sort.SliceStable(results, func(i, j int) bool {
        if results[i].Score != results[j].Score {
            return results[i].Score > results[j].Score
        }
        return results[i].ID < results[j].ID
    })
    return results
}
```

### 4.3 三个值得讲的细节

#### ① 每路都归一化到 [0, 1]

**为什么必须归一化**：

- vec_dist 理论范围 [0, 2]，但实际文本一般 [0, 1] 之间
- tag_overlap 是计数（如 0/1/2/3），尺度差异巨大
- difficulty 差是 -4 到 +4
- **如果不归一化直接加权，量纲不一致权重就没意义**

#### ② 输出保留三路子分（不只是 final score）

```go
type Result struct {
    Score           float64  // final
    VectorScore     float64  // 子分 1
    TagScore        float64  // 子分 2
    DifficultyScore float64  // 子分 3
}
```

**为什么保留子分**：

- 调试时能看到"这题是 vector 主导命中还是 tag 主导命中"
- A/B 实验时可以做相关性分析
- 给用户/面试官解释"为什么推这道题"

#### ③ score 相同时按 ID 稳定排序

```go
sort.SliceStable(results, func(i, j int) bool {
    if results[i].Score != results[j].Score {
        return results[i].Score > results[j].Score
    }
    return results[i].ID < results[j].ID   // tie-breaker
})
```

**为什么需要**：

- 没 tie-breaker 时 `SliceStable` 仍然稳定但**输入顺序决定结果**（PG UNION 顺序不保证）
- 加 ID 排序后**同样的输入永远得到同样的输出**
- 单测可以 `require.Equal(t, expected, actual)`，否则要写"集合相等"判断

## 五、离线 reindex CLI（与在线服务解耦）

### 5.1 命令行

```bash
# 从 JSON seed 重建所有 embedding
go run ./cmd/reindex -seed seeds/question_bank.json -mode real

# 仅 dry-run（不写 DB）
go run ./cmd/reindex -seed seeds/question_bank.json -mode mock -dry-run

# 增量更新（只重算 embedding 为 NULL 的题）
go run ./cmd/reindex -mode real -only-missing
```

### 5.2 为什么独立 CLI 而不放进 server 启动流程

| 选择 | 优点 | 缺点 |
|---|---|---|
| 启动时自动 reindex | 简单，一条命令搞定 | **每次启动慢几分钟，影响 SLO**；多实例重复算 |
| ✅ **独立 CLI** | 启动快、运维可控、定时任务/手动触发 | 多一步部署 |

**与在线服务解耦的好处**：

- 调整 embedding 模型时**先重建索引，再切流量**
- reindex 失败不影响在线
- 可以定时跑（如每周更新）

### 5.4 启动时维度强校验

```go
// cmd/server/main.go 启动校验
dim := embedder.Dimension()
dbDim := getEmbeddingVectorDim(pool)   // 读 information_schema
if dim != dbDim {
    log.Fatalf("embedding dim mismatch: embedder=%d, db=%d", dim, dbDim)
```

**为什么必须校验**：

- 启动就 fail 比运行时报怪错好 100 倍（`ErrPermanent` 范畴）

## 六、retrieve_rag 节点：把检索集成进图

```go
// internal/nodes/retrieve_rag.go
func RetrieveRAG(ctx context.Context, sess *domain.Session) error {
    // 1. 基于 JD + GapReport 构造查询
    query := buildQueryFromGap(sess.JobProfile, sess.GapReport)

    // 2. Embedding 查询文本
    vec, err := embedder.Embed(ctx, query.Text)
    if err != nil {
        // ❌ 不要静默 fallback 到固定题库
        // ✅ 显式降级 + 记 DegradedReasons
        markDegraded(sess, "rag", "embedding_failed: " + err.Error())
        sess.CandidatePool = fallbackQuestionBank
        return nil
    }

    // 3. 调 Retriever（pgvector or fallback）
    results, err := retriever.Retrieve(ctx, retriever.Query{
        QueryEmbedding:   vec,
        Tags:             query.Tags,
        Difficulty:       query.TargetDifficulty,
        K:                10,
        VectorCandidates: 50,
        TagCandidates:    30,
    })
    if err != nil {
        markDegraded(sess, "rag", "retrieve_failed: " + err.Error())
        sess.CandidatePool = fallbackQuestionBank
        return nil
    }

    sess.CandidatePool = resultsToQuestions(results)
    return nil
}
```

### 6.1 fallback Retriever（PG 不可用时）

```go

if cfg.PG.DSN != "" {
```

- `run.json.config.retriever` 字段会明确记录 `pgvector` 或 `fallback`，让 demo 报告里能看到差异

## 七、可能的追问与回答

### Q：为什么用 pgvector 而不是 Milvus / Qdrant？

**A**：核心理由是**不引入新组件**：

- 项目已经用 PG 做业务存储（sessions 表 + question_bank 元数据）
- pgvector 让 **向量字段和业务字段在同一事务**，避免跨服务一致性问题
- 单题库规模（1万 ~ 10 万题）pgvector 完全够用，HNSW 召回延迟 < 50ms
- 100 万 ~ 1 亿规模才有必要上 Milvus；那时候业务体量也够请运维同学了

### Q：为什么 cosine distance 而不是 L2 / inner product？

**A**：
- embedding 已经归一化（DashScope text-embedding-v3 输出 unit vector），三种度量在归一化空间等价
- cosine 直觉上更易解释（"语义相似度"），团队沟通无需展开数学
- pgvector 支持三种，**接口预留切换能力**（pgvector.go 里只改一个算子）

### Q：HNSW 索引怎么建的？

**A**：
```sql
CREATE INDEX question_bank_embedding_hnsw
  ON question_bank
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

- `m = 16`：每层节点的邻居数（默认 16，平衡精度/内存）
- `ef_construction = 64`：建索引时的搜索宽度（越大索引质量越高，建索引越慢）
- 查询时再用 `SET LOCAL hnsw.ef_search` 控制召回精度

### Q：tag 是怎么提取的？

**A**：
- 入库前**人工标注 + LLM 辅助提取**
- 标注规范：技术领域（go/redis/mysql）、子主题（concurrency/transaction/index）、能力维度（API使用/原理/调优）
- 入库时 `CanonicalizeTags` 做标准化（小写、去空格、同义词映射）

### Q：评估 RAG 质量怎么做？

**A**：当前没做形式化评估（在 HANDOFF TODO 里），但有思路：

- **Faithfulness**（答案忠实于检索结果）：让 LLM 判 evaluator
- **Relevance**（检索结果与 query 相关）：人工标注 + NDCG
- **Completeness**（检索覆盖率）：标注 ground truth 题目，看是否被召回

参考项目（如 RAGAS / TruLens）的三维评估体系。

### Q：如果向量索引被删了/数据丢了怎么办？

**A**：
- 启动时维度校验会失败 → server 直接报错退出
- 运维路径：跑 `make migrate-up` + `go run ./cmd/reindex -seed seeds/question_bank.json -mode real`，几分钟重建
- 业务影响：在线服务会 fallback 到本地 question bank（功能可用，召回质量下降）

### Q：你这套方案 QPS 能到多少？

**A**：单实例 PG（无副本）：
- HNSW 召回（`ef_search=100`）：单次 ~30ms
- 整个 retrieve_rag 节点：~50ms（包括 embedding + SQL + fusion）
- **瓶颈在 embedding API**（~200ms），不是 PG
- 实际 RAG QPS 取决于 embedding provider 配额
