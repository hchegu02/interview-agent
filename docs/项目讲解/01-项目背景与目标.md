# 项目背景与目标

> 用途：面试官问"你做这个项目的动机 / 解决什么问题"时的标准答案
> 阅读顺序：业务动机 → 技术挑战 → 架构目标 → 技术选型
> 一句话核心：**用工程化的方式驯服 LLM 的不可控性，做一个真能多实例部署的 AI Agent**

---

## 一、业务动机

### 1.1 真实痛点

我自己面试时遇到的痛点：

| 痛点 | 现状 | 影响 |
|---|---|---|
| 模拟面试**没有真实感** | 自己背题、找朋友帮忙问 | 紧张感不真实、反馈不专业 |
| 题目**不贴合岗位** | 通用题库，跟 JD 关系不大 | 准备 1 个月，面 8 个不同方向 |
| 回答**得不到深度评估** | 只能自己判断对错 | 不知道哪里答得好 / 不好 |
| 反馈**不可追踪** | 朋友说"还可以"就过去了 | 没法系统提升 |
| 不能**反复练** | 真人面试机会有限 | 想刷 100 次不可能 |

### 1.2 现有方案的不足

| 方案 | 优点 | 缺点 |
|---|---|---|
| **真人模拟面试**（猎头、付费教练）| 反馈深度 | 贵（300+ /次）、不能 7×24 |
| **背题** | 0 成本 | 没有交互、不能追问 |
| **ChatGPT 直接对话** | 灵活 | **没有连贯流程**，每次都从零开始 |
| **市面上的 AI 面试产品** | 有产品形态 | 大多是简单封装 LLM，**没有 Agent 编排、没有 RAG、没有多实例可靠性** |

### 1.3 我的目标

做一个**真能用的 AI 面试 Agent**：

- ✅ 上传 JD + 简历，自动生成贴合的题
- ✅ 多轮对话（出题 → 答题 → 追问 → 评分），不是单次问答
- ✅ 评估**有深度**（覆盖点、漏点、提升建议）
- ✅ **可重复练**（每次 session 独立，可对比进步）
- ✅ **生产级稳定性**（不是 demo，要能真上线给陌生用户用）

## 二、技术挑战（为什么这个项目有难度）

### 2.1 LLM 是慢且不稳定的依赖

| 维度 | 普通 CRUD 后端 | LLM 后端 |
|---|---|---|
| **延迟** | DB 查询 ~50ms | LLM ~3-5 秒 |
| **可用性** | 数据库 99.95% | LLM provider 99%（限流 / 抖动很常见）|
| **错误率** | < 0.01% | **可能 5% 输出 schema 不符合预期** |
| **成本** | 几乎为零 | **按 token 计费，单 session $0.1-1** |
| **可重试性** | 完全可重试 | 错误分类决定是否重试 |

**意味着**：

- 必须有**熔断 + 限流 + 背压**（亮点 3）
- 必须有**降级路径**（LLM 失败 → 规则评分）
- 必须有**重试 / schema 自纠**（亮点用到的 `CallWithSchema`）
- 必须**显式标记降级**让用户知道（亮点 4）

### 2.2 Agent 流程是有状态的多步对话

| 维度 | 普通 API | Agent 流程 |
|---|---|---|
| **请求模型** | 一次 request / response | 多轮交互，每轮可能调多次 LLM |
| **状态** | 无状态（RESTful）| 有状态（Session + WorkingMemory）|
| **流程控制** | 简单 if/else | 多分支 / 循环 / 并发 / 暂停恢复 |

**意味着**：

- 需要**编排框架**（DAG / state machine）
- 节点需要**挂起等用户输入再恢复**（Suspend/Resume）
- 状态需要**持久化**支持跨请求 / 跨实例
- → 自研 Graph 框架（亮点 1）

### 2.3 真实部署需要多实例

| 单实例 | 多实例 |
|---|---|
| 重启就丢 session | 跨实例 takeover |
| 没法水平扩展 | 加机器加吞吐 |
| 维护时停服 | 滚动发布无感 |

**意味着**：

- 需要**分布式协调**（Lease + Snapshot，亮点 2）
- 需要**事件总线跨实例**（Redis Streams，亮点 6）
- 需要**Session 持久化 + 状态迁移**（亮点 7）

### 2.4 题库不能是固定的

| 固定题库 | RAG 检索 |
|---|---|
| 题目重复 | 每次根据 JD/简历动态选 |
| 不能覆盖新技术 | 题库 reindex 增量更新 |
| 难度匹配靠运气 | 多路特征融合 |

**意味着**：

- 需要**向量检索 + 多路融合**（亮点 5）

## 三、架构目标（北极星指标）

设计这个项目时给自己定的几条**硬约束**：

### 3.1 工程目标

| 目标 | 衡量方法 |
|---|---|
| **真能多实例部署** | 集成测试覆盖跨实例 Takeover 场景 |
| **LLM 挂了不影响用户体验** | 节点降级路径 + 报告里提示 "[评估]环节降级" |
| **节点单测无需 mock IO** | 所有副作用走 Callback，节点测试只关心业务逻辑 |
| **5 分钟能跑完端到端 demo** | `make demo-mock` 一键 |
| **新人 onboard 0.5 天能改第一个节点** | CLAUDE.md + HANDOFF.md + Makefile help |

### 3.2 反目标（明确不做的）

| 不做 | 为什么 |
|---|---|
| ❌ 多模态（语音、视频）| 文本已经能覆盖 80% 价值，多模态 ROI 低 |
| ❌ 用户管理 / 鉴权系统 | 项目重心是 AI Agent 不是 SaaS 全家桶 |
| ❌ 复杂前端 | CLI + Postman + smoke 脚本足够演示 |
| ❌ k8s 完整 Helm chart | 单机 Docker 够用，k8s 是 TODO |
| ❌ A/B 实验框架 | 个人项目用不上 |
| ❌ 用户行为分析 | 同上 |

**有所不为，才能做好该做的**。

## 四、技术选型理由（10 个关键决策）

| # | 决策 | 选 | 不选 | 理由 |
|---|---|---|---|---|
| 1 | 语言 | **Go 1.25** | Java / Python | 单 binary 部署、并发模型契合 Agent、性能好 |
| 2 | HTTP 框架 | **Gin** | Echo / net/http | 中间件生态成熟、路由清晰 |
| 3 | Graph 框架 | **自研** | Eino / LangGraph | 强约束 + 边界小 + Suspend/Resume 直接实现（亮点 1）|
| 4 | DB | **PostgreSQL** | MySQL | JSON + pgvector + 事务支持 |
| 5 | 向量库 | **pgvector** | Milvus / Qdrant | 不引入新组件 + 业务表事务一致（亮点 5）|
| 6 | 缓存 / 协调 | **Redis** | Memcached / etcd | KV + Streams + Lua 一栈搞定（亮点 2/6）|
| 7 | LLM | **OpenAI 兼容**（通义千问）| OpenAI 直接 | 国内合规 / 价格低 / 兼容性好 |
| 8 | Embedding | **DashScope text-embedding-v3** | OpenAI | 与通义千问同生态、价格友好 |
| 9 | Redis 客户端 | **手写 RESP** | go-redis | 只用 9 个命令，~120 行替代依赖（亮点 6）|
| 10 | 日志 | **slog**（标准库）| zap / zerolog | 标准库优先、结构化、性能足够 |

### 4.1 三个最关键的决策（面试官最可能问）

#### ① 为什么自研 Graph 而不用 Eino

> Eino 是字节出的优秀框架，但**强约束更难做**——我自研可以强制 Router 纯函数 / 节点错误分类 / WorkingMemory 强类型协议，长期可维护性更好。**~500 行的自研框架边界小、规则清晰、能讲清楚每一段设计**；引 Eino 后工程亮点会被框架吞掉。详见亮点 1。

#### ② 为什么 pgvector 而不是 Milvus

> 核心理由**不引入新组件**——项目已经用 PG 做业务存储（sessions、question_bank 元数据），pgvector 让向量字段和业务字段在同一事务里，避免跨服务一致性。单库 1-10 万题完全够用，HNSW 召回延迟 < 50ms。规模到 100 万 ~ 1 亿才有必要上 Milvus。详见亮点 5。

#### ③ 为什么手写 RESP 协议

> 项目只用 9 个 Redis 命令（XADD/XREAD/XREVRANGE/SET/GET/DEL/EVAL/AUTH/SELECT），手写 ~120 行就能搞定。go-redis 是好库但 overkill；**自己写让我对 RESP 协议和 Stream 嵌套结构理解深入**，面试时能讲细节。零依赖也是工程优势。详见亮点 6。

## 六、和其他类似项目的对比

### 6.1 对比 AutoGPT / BabyAGI

| 维度 | AutoGPT / BabyAGI | 本项目 |
|---|---|---|
| 目标 | **通用 Agent**（任意任务）| **领域 Agent**（面试评估）|
| 流程 | 自由生成 plan | **固定 DAG，可控**|
| 部署 | 单机脚本 | **多实例生产级** |
| 状态 | 内存 | **持久化 + 跨实例** |
| 失败处理 | 整体重跑 | **细粒度降级** |

> AutoGPT 是科研演示，本项目是**工程化领域 Agent**——后者更难，因为要把 LLM 的不可控性约束在工程边界内。

### 6.2 对比 LangChain Agent / LangGraph

| 维度 | LangChain / LangGraph | 本项目 |
|---|---|---|
| 语言 | Python | **Go** |
| 部署 | Python 依赖管理痛苦 | **单 binary** |
| 性能 | GIL 限制并发 | **goroutine 天然并发** |
| 框架重量 | 重 | **~500 行自研** |
| 业务深度 | 通用 | **针对面试场景定制** |

### 6.3 对比 Eino

| 维度 | Eino | 本项目 |
|---|---|---|
| 来源 | 字节开源 | 自研 |
| 强约束 | 框架限制少 | **Router 纯函数 / 节点错误分类强制** |
| 挂起恢复 | 嵌套 Runnable + Callback | **ErrSuspended + CurrentNode（更简单）**|
| 学习曲线 | 需要懂框架 | 通用 Go 知识即可 |

> Eino 是优秀生产框架，**团队协作 / 多人项目用 Eino 更合适**。本项目自研是为了"边界小、规则清晰、能讲清每一段"。

## 七、面试时怎么用这份文档

### 7.1 项目面开场（2 分钟）

> "我做这个项目的动机是**自己面试时的真实痛点**——找不到能既贴合 JD、又能多轮追问、又能给深度反馈的工具，市面上的产品大多是简单封装 LLM，没有 Agent 编排，没有 RAG，更没有多实例可靠性。
>
> 所以我自己做了一个，**重点不是堆 LLM 功能，而是用工程化的方式驯服 LLM 的不可控性**——比如自研 Graph 框架做编排、三层防护应对 LLM 慢且不稳定、Redis Lease 做多实例协调、显式降级让用户感知 LLM 故障。
>
> 整个项目 ~5000 行业务代码 + 6000 行测试 + 3000 行文档，**已经能多实例部署，5 分钟跑通 end-to-end demo**。"

### 7.2 被问"为什么不直接调 API"

> "调 API 只是项目的一小部分。**核心难度在于：LLM 是慢（3-5 秒）、不稳定（限流/抖动）、按 token 计费的依赖**。
>
> 我用三层防护（背压 + 熔断 + 限流）保护它、用显式降级让用户感知故障、用 schema 自纠重试应对输出不一致、用多实例 Lease 让面试不会因为单机宕机中断。
>
> **真把 LLM 用到生产，工程量远比 demo 大**。"

### 7.3 被问"这项目有什么创新"

> "技术创新可能不多——分布式协调用 SET NX EX、熔断器用经典三态机、RAG 用 pgvector，都是成熟方案。
>
> **创新点是组合方式 + 工程边界**：
>
> 1. **自研 Graph + Suspend/Resume**：在 ~500 行内实现支持多实例的 Agent 编排（亮点 1）
> 2. **错误分类驱动的熔断**：哪些错算 / 不算熔断有显式规则（亮点 3）
> 3. **降级 vs 阻断的判断纪律**：写进 CLAUDE.md 的硬规则（亮点 4）
> 4. **手写 ~120 行 RESP 协议替代 go-redis**（亮点 6）
> 5. **从 Notes 弱协议演进到强类型 + Migration**（亮点 7）
>
> **每个都不是新概念，但组合起来 + 有取舍 + 能讲清楚——这是工程能力的体现**。"
