# 业务试用 Runbook

本文档用于业务、HR、面试官参与 Interview Agent 内部试用。目标是验证候选人面试体验、报告可读性、项目润色入口和反馈闭环是否满足试用预期。

## 1. 适用对象

- 业务负责人：关注岗位匹配度、候选人回答质量、报告是否能辅助筛选。
- HR：关注面试入口是否顺畅、流程是否容易说明、报告是否便于流转。
- 面试官：关注问题质量、追问是否合理、评分和建议是否符合真实面试判断。

试用者只需要按本文档完成固定脚本并提交反馈，不需要理解系统内部实现。

## 2. 非生产边界

- 这是内部试用，不是生产发布，不对外开放，也不代表正式服务承诺。
- 请使用内部指定账号、候选人样例和公开 GitHub URL，不要输入真实候选人的敏感信息。
- 前端只展示后端状态；如果页面显示失败、等待、报告缺失或工具结果异常，请按问题模板记录，不要自行判断底层原因。
- 本轮试用关注产品流程、内容质量和问题记录，不要求业务试用者排查技术细节。
- 任何反馈都不要包含密钥、私有仓库地址、完整简历、完整面试回答或其他敏感材料。

## 3. 固定试用脚本

每位试用者至少完成一次完整脚本。建议使用内部提供的候选人样例和岗位样例，保证不同试用者结果可比较。

1. Start one interview / 开始一次面试
   - 打开内部试用入口。
   - 选择或填写指定岗位、候选人样例和面试场景。
   - 点击开始面试，确认页面进入面试状态。

2. Answer the main question / 回答主问题
   - 阅读系统给出的主问题。
   - 用 3 到 8 句话回答，内容应接近真实候选人的口吻。
   - 提交回答后，观察页面是否进入下一步。

3. Answer one follow-up when present / 有追问时回答一次追问
   - 如果出现追问，选择其中一次追问进行回答。
   - 回答可以补充例子、澄清背景或承认不足。
   - 如果没有追问，记录“本轮无追问”，继续查看报告。

4. Review the report / 查看报告
   - 完成面试后打开报告。
   - 检查报告是否包含总体结论、优势、风险点、建议和评分说明。
   - 判断报告是否能辅助 HR 或面试官做下一步决策。

5. Submit one `project_polish` request with a GitHub URL
   - 在项目润色入口提交一次请求。
   - 请求中必须包含一个公开 GitHub URL。
   - 检查返回内容是否围绕项目表达、简历描述或面试讲述给出可执行建议。

6. Fill the feedback template / 填产品反馈模板
   - 按“反馈提交”章节填写一次产品反馈。
   - 如果遇到阻塞，额外按“遇到阻塞时怎么记录”章节补充问题记录。

## 4. 面试流程检查点

完成面试脚本时，重点检查以下问题：

- 是否能顺利开始一次面试。
- 主问题是否清楚，是否符合岗位和候选人背景。
- 回答提交后页面状态是否明确，没有让人误以为卡住。
- 追问出现时是否自然，是否围绕候选人刚才的回答。
- 没有追问时，流程是否能继续到报告。
- 报告是否能被 HR 和面试官读懂。
- 评分、优势、风险点和建议是否相互一致。
- 报告中是否存在明显误解、空泛评价、过度肯定或无依据扣分。

## 5. 项目润色检查点

提交 `project_polish` 请求后，重点检查以下问题：

- GitHub URL 是否被页面接受。
- 页面是否清楚展示当前处理状态和最终结果。
- 返回内容是否围绕项目背景、技术亮点、业务价值和面试表达展开。
- 建议是否具体，能否直接帮助候选人改简历或准备项目讲述。
- 如果返回失败，页面是否给出可记录的状态或提示。
- 内容是否避免夸大项目经历，是否提醒候选人基于事实表达。

## 6. 反馈提交

每次试用结束后，请提交一条产品反馈。建议使用以下模板：

```text
试用者角色：
试用日期：
岗位或场景：
是否完成固定脚本：是 / 否

面试流程评分（1-5）：
报告可用性评分（1-5）：
项目润色可用性评分（1-5）：

最有价值的部分：
最影响使用的问题：
希望下一轮优先改进：
是否适合扩大内部试用：是 / 否 / 不确定
补充说明：
```

评分含义：

- 1：无法使用或严重影响判断。
- 2：能看到功能，但问题明显。
- 3：基本可用，需要明显改进。
- 4：可用于内部试用，有少量问题。
- 5：体验稳定，内容质量接近可推广。

## 7. 扩大内部业务试用条件

- 固定脚本已完成。
- 面试流程、报告可用性和项目润色评分均在 1-5 范围内，并有明确扩大建议。
- 存在阻断项时，不得标记为适合扩大内部试用。
- 维护者必须运行 `go run ./cmd/internal-trial-smoke`，并确认输出 `business_trial: feedback evidence verified`。
- 该条件只允许扩大受控内部业务试用，不代表生产上线批准。

## 8. 遇到阻塞时怎么记录

遇到工具、报告或面试流程问题时，不要反复重试覆盖现场。请按以下模板记录：

```text
问题类型：面试流程 / 报告 / 项目润色 / 页面状态 / 其他
发生时间：
试用者角色：
入口页面或功能：
使用的岗位或场景：
GitHub URL（如适用）：

操作步骤：
1.
2.
3.

期望结果：
实际结果：
页面显示的状态或提示：
是否还能继续完成固定脚本：是 / 否
是否包含敏感信息：是 / 否
截图或附件位置（如有）：
```

记录原则：

- 只记录复现问题所需的最小信息。
- 可以记录页面显示的错误状态、按钮名称、报告章节名称和简短摘录。
- 不要粘贴完整面试回答、完整报告、私有链接、密钥或候选人敏感信息。
- 如果问题阻塞继续试用，请停止本轮脚本并提交问题记录。
